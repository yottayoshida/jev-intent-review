# Changelog

All notable changes to this project are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Removed

- **The generic run: repository-wide discovery, the relevance, satisfaction and completeness questions, and the verdict per requirement** (ADR 0007, replacing ADR 0002). `jev-intent-review` with no flag now does what `--experimental-local-check` did: the calls of the functions the change touched and their callers one hop out are read under each requirement's form, and each is reported as worth checking, holding, not settled or not required of. No VERIFIED, VIOLATION or UNKNOWN is stated anywhere. The flag is still accepted — the report and the exit code are the same without it, and one line on stderr says so; `--experimental-candidates-only` is `--candidates-only`, with the old name accepted. **In a language other than Rust no function is read and no call is asked about; only the change question runs** — the generic run had read any language. The benches that drove the generic run and the questions they sent are kept under `bench/generic/`, outside the type check, for the logs they produced.

### Changed (breaking)

- **`--json` is `version: 2`**, one shape for every way a run ends (skipped, stopped for want of readable requirements, `--candidates-only`, finished): `exitCode`, `skipReason` when skipped, `intent`, `sources`, `requirements` (the readings per call, as the local check printed them), `unexpectedChanges`, `sent` (`requests`, `bytes`, `answered` — the requests Jev answered, in the same unit as `requests` — and the endpoint and host) and `metadata`. Gone: `verdict`, `discovery`, and the per-requirement `status`, `coverage`, `scope` and `candidates`; a stopped run's separate `{revisions, sources, intent, notes}` shape, whose `notes` are now `metadata.notes`. Everything the generic run used to call a blocker or note beside the verdict — intent that exists and was not checked, a change to this tool's configuration or to a GitHub Actions workflow, requirements only from the pull request's own description, what the pass over the changes left out or redacted — is a note in `metadata.notes`, printed under `## Notes`. The Markdown report names its requirements' sections and the change question's; `Coverage` and the per-place lines are gone, `--candidates-only` says the set was built and nothing was asked, and `Sent to the judgment model` says how many requests were answered.
- **`policy.fail_on` defaults to `[]`, and its value is `finding`.** A call worth checking leaves the exit code at 0 unless the repository's `.jev-intent-review.yml` says `policy.fail_on: [finding]`, which exits 1 when any call is. A file that says `violation`, the value 0.1 knew, is read as `finding` and the notes say so. `policy.unknown`, `intent.pr_body_only: unknown`, `discovery.*`, `judgment.satisfaction_probability`, `judgment.relevance_probability` and `evidence.max_related_chars` no longer apply: a file that sets one is not refused, and the notes say which and why. They go in the next minor version.
- **A function's calls are listed up to 1,000, where it was 40, and a function whose body opens below a line of its own signature has its body read** (#38). The listing stopped at a function's fortieth call, so a call past it was gone before any budget ordered it — grovedb#500's unchanged caller calls the changed `finalize` past its fortieth, and is now inside the budget (7th of 18). And it read the line `) -> Result<…>` at the function's indent as the function's end, so a function whose body opens below it — a `where` clause, a return type over several lines, `{` on a line of its own — was listed as no call at all, with nothing in the notes; whatsapp-rust#759's fixed function, quebec#136's changed one and omamori `#468`'s `mutate_config` are written that way, and are read now. The line the body opens on is looked for at the function's own indent only, so a one-line function, a doc example and a pattern in the parameters are read as before. `BlockIndex.enclosing`, which the changes' question, the siblings' spans and the evidence use, reads a function's end the same way since #74, and a bare block just inside such a body, a `where … {` on one line and a `pub(in path) fn` too: every body line of the 4,292 such functions on five repositories is that function's (up to the 300 lines a block is read whole), checked against bodies found by counting brackets, no line outside Rust reads differently there, and the changes' question asks 418 regions where it asked 421 on the acceptance runs — nameless pieces joined into the functions they are part of — so kept answers for a moved region are asked again once. A `where {` written at column 0 opens its method's body, which ends at the method's own indent, not at the `impl`'s. A Rust `fn new` is listed and named: it was kept out as JavaScript's `new Foo(` is, so every constructor's calls were missing from the listing (98 on the five repositories among the functions above, each listed now), and `fn switch` and `fn with` were nameless the same way. A call the listing reads no longer comes from the signature (a `where` clause's `Fn(…)` read as a call). What the cap still leaves out is counted in the notes, for the files read for the siblings too, and a function it cut is still not taken for a sibling. Measured without a request on the 20 runs of `bench/budget-by-origin.ts` (log `bench/logs/budget-by-origin-v2.json`): every known target inside the budget, no call on a changed line and no changed function losing its question; on moltis#1064 the changed functions ask 18 or 19 calls where they asked 4 or 5, so the callers — who get 10 and what those leave — ask 11 or 12 where they asked 25 or 26 (its unchanged caller's call 20th of 30, where it was 6th). The siblings change with what is read (pybun#428 5 → 19, whatsapp-rust#759 2 → 0), within their budget of 10. A run can take about twice as long (moltis#1064 17 → 30–34 s set-built-only) and print a much longer report (pybun#428 153 → 821 KB, most of it *Not checked*). Against Jev, three runs each on grovedb#500 and whatsapp-rust#759 (`bench/logs/calls-per-function-jev-v1.json`): both unchanged-caller and fixed calls asked and read as holding; one call newly asked on whatsapp-rust#759 was listed in every run and is counted as a false listing (three labellers, two to one).
- **The callers one hop out have a budget of their own** (#38, ADR 0015). A requirement's 20 calls are the functions the change touched alone now, in the order they had when they shared them — every call that was reached then is reached now; their callers get 10 plus whatever the changed functions left of their 20, the calls into a changed function first across every caller, then the rest, each one per caller at a time. Every requirement's changed functions are asked first, then the changes' questions, then every requirement's callers, then the siblings, so a request limit, the pull request's limit or the time reached in the middle of a run stops at the callers and never at a changed function or a question about a change; with `--trace`, a requirement's `worth checking of N read` line comes after the callers. Up to 10 more calls — 20 more requests — per requirement where callers exist; the two budgets never ask more than 30 calls together, and the siblings' 10 stay apart and last. On Kontor#385 the unchanged caller's call into the function the pull request changed (`initiate_rollback` → `get_decided_from_anchor`), 53rd of 75 in the shared budget, is 2nd in the callers'. In `--json`, `counts.budget` is what the two could ask together (30 by default, where it was 20), and `counts.byOrigin.changed` and `counts.byOrigin.calls_changed` count each in the terms of `counts.siblings` (additive; still `version: 2`); the report prints a line for each, and a caller's call left over is under *Not checked* as "the callers' budget of N was already spent". The order of `wouldAsk`, `observed`, `findings` and the left-over rows of `unchecked` changes with it, so a pull request's first run after this update reuses fewer kept answers (ADR 0013). The callers can still get fewer than the shared budget gave them where the changed functions have many calls and few turns; with more than ten callers, the calls into a changed function take the whole callers' budget. The split was chosen on Kontor#385, a regression case, and the other runs of the comparison only show that nothing got worse on them (`bench/budget-by-origin.ts`, log `bench/logs/budget-by-origin-v1.json`).
- `metadata.questionsHash` now fingerprints what a run can send — the change question and the two forms' questions — where it used to cover the generic run's questions only.
- An observation request that fails, or a host that answers nothing usable over both the calls and the changes, is handled as before for the calls; a run whose only questions were the changes' (a repository the local check reads no function in) and got no answer now fails with exit 12 like any other.

### Added

- **The retrospective's protocol, version 3, and the tool that screens its sealed rows** (#89, `bench/eval/RETRO.md`, `retro/screen.ts`, `retro/checks.ts`). Before any sealed row is read: a row is a case once its original is found, the fix's own material is complete and the screen keeps the fix — the writer and the checker are not filters, and a case caught before the merge is its repository's one case, out of the 17. The yield check is counted in repositories and against the first 800 rows: go on when `3·c·M ≥ 68·r`. The sealed records move to the sandbox's `batches` branch; this repository keeps a batch's counts and sha256. `screen.ts` prints only counts, begins a row only when its worst case (32 runs) fits, and resumes at the first row not decided; the retrospective's tools now read a child process's output instead of passing it through. The search now reaches the date floor: 1,471 rows over 2026-07-01 to 09-23, 552 repositories in the first 800 (`M`).
- **A third form, `failure_handling`: a failure may be returned, logged or recorded, and must not be turned silently into a success** (#85, ADR 0023). Named in the spec only (`"form": "failure_handling"`): the question that asks Jev which form a sentence says does not offer it, and its measured hash does not change; an answer naming it reads as the default. Each call is asked what the function does with its failure — `propagates`, `reports_locally` (a log, a warning, standard error, a record, or a value the caller can tell from a success), `continues_silently` (no trace: an empty or default value the caller cannot tell from a success, with nothing logged, is this) or `cannot_determine` — and a call is worth checking on `continues_silently`. It is asked in any function whose callee returns a `Result`, one that returns `()` included, where `failure_propagation` asks only in a function that returns one (a sibling of the change still returns one, under every form). The observation question was measured before it was wired, on packets built as the run builds them, with the lines committed first (`bench/handling/`, `bench/logs/handling-probe-v1.json`, 51 requests): on four places of grovedb#500 and moltis#1064, every shipped and rewritten version read as `propagates`, every version that drops the failure as `continues_silently` — a version that logs something else in the same function among them — and every version that logs it as `reports_locally`, three runs of three, lowest 0.87. `--json`'s `form` can be `failure_handling`; `metadata.questionsHash` moves, and no kept answer is asked again (its key is the request, and the other forms' requests do not change a byte). How many of the evaluation pool's 91 labelled rows each form's sentence can write is recorded in `bench/eval/forms-85/` (three fresh annotators per form; `bench/eval/PROTOCOL.md`, *Labels*, notes it; version 4 unchanged). Not claimed: how it answers in a function that returns `()` (the four functions of the probe all return a `Result`), or its reach, precision or stability on pull requests it was not built on.
- **How #80's sealed set is chosen, fixed before its first candidate is read** (#80; `bench/eval/PROTOCOL.md` version 4). Candidates are screened in batches whose verdicts, requirements and cases live only in the private sandbox; this repository holds each batch's range of rows read, rows kept and the sha256 of its verdicts (`bench/eval/sealed-batches.json`, shared with #89, lines only added), and a repository's side is salted with the first main merge commit holding that hash — found by the hash and checked against git by a test, so a later merge commit does not pass, and each measurement's batches run on from row 1, so no row is judged again in a later batch to draw its side a second time. #89's search leaves out the repositories of #80's `search-v2.json` too. Screening adds: no licence screens a repository out (any licence will do), a fork or copy counts as the repository it copies, one case per repository, dependencies may be fetched to build but the observation runs offline, and an hour a candidate. `search-v1.json` was cut at 100 on three of its four phrases, so a second search (`bench/eval/search-v2.json`) takes the same phrases over 2026-01-01 to 2026-06-30, split until none is cut, before any of its rows is read. The cap is 800 rows, and after the first 100 the yield decides whether 17 sealed repositories can be reached at all. `retro/search.ts`'s `searchRange` takes its phrases as an argument (the default unchanged).
- **The retrospective's protocol, version 2, and the calibration of its hindsight check** (#89, `bench/eval/RETRO.md`, `retro/calibrate.ts`). Version 1 had no step asking whether a later fix fixed a failure-handling defect at all; version 2 screens F with three annotators on `PROTOCOL.md`'s labels and keeps the four where the code before F did not bring the failure to the caller, with the steps that run no annotator first. The hindsight check is calibrated on dev before any sealed candidate: ten requirements written from the original pull request alone and the same ten with a function the fix changed named in them, shuffled; it passes at 9 of 10 named left out and at most 1 of 10 clean. It shows the check catches a name the fix told, not a requirement that picks the fix's call in the bundle's own words. The second checking of the twenty, a fix-aware writer's ten and the screen against #80's labels are recorded, never in the verdict. `retro/search.ts --dev` searches the split's dev repositories into `retro/search-dev-v1.json`, never the sealed search. Runs of `claude -p`: at most 250 (owner), stopped there; an answer that cannot be counted is asked again three times, then the run stops.
- **The code a reading turns on is sent with the packet, or the call is not asked about** (#82, ADR 0019, ADR 0020). Each form names, from the body's text and without asking Jev, what its answer turns on. Under `failure_propagation`, a call whose failure is passed to one of this repository's own functions before it reaches `?` (`step_outcome(self.rewrite_heights(v))?`) is not asked about — its body is not sent, and what the function returns is that function's to say — and is under *Not checked* with the function named; a failure returned first, or passed through a method or a name every repository has, is asked as before. Under `check_before_action`, the checks above the call — calls in an `if`, `while`, `match` or its guard, in `ensure!` or `assert!`, in a `let … else`, or the whole of a statement that `?`-s its result and binds nothing, whose own name meets the requirement's words — go with the packet: each body when its name has one definition outside the tests and it fits (4,000 characters each, 8,000 in all), and the functions those bodies call, one level down, while there is room. A check with more than one definition, or too long, holds the call. The report lists the bodies sent under each call (`sent with it`), names a second level that did not go (`not sent`), and `--json` carries `sent` and `notSent` on observed calls and findings (additive; still `version: 2`). **The words of the check form's function question change** (`metadata.questionsHash` moves; every answer kept for a pull request under that form is asked again once): it assumes the case the requirement describes, says the bodies under `evidence.related` are those of functions the function calls, and that every other operation succeeds unless the case itself decides it — where it used to assume that "the check it asks for does not pass", which handed Jev the check by name. Measured before it was wired, on the same packets with the old words as the control, interleaved (`bench/decisive/words-probe*.json`, `bench/logs/words-probe-v[1-4].json`, 848 requests): on the three cases' targets in five versions — the new **helper** version moves the check into a helper that checks, the same call sites as the hidden one — the new words read every hidden version as the defect it is and every helper as holding, where the old words read moltis#1064's hidden version as holding (0.86–0.89) with the helper's body in the packet; on twelve sentences over four pull requests the rules were not written on, of 25 runs the old words held, the new words held 21, read 3 under the bar, and read one — a call the sentence does not govern — as reaching at exactly 0.60, which the owner recorded as the line's coarseness and adopted. A two-step that reads each check's value from its own body first was measured beside it and is not adopted: it read one three-line body (`{ true }` under a doc comment and a double-negative sentence) as `false` three times of three. Asking Jev whether the code sent is enough was measured first and is not adopted either (`bench/evidence-settles/`): Jev could not tell which unsent call decides. What is not promised: a failure passed through a method (`.map_err`, `.ok()`: the repositories measured define their own), a constructor or a macro, or a variable over several statements; a check not in a condition, whose name does not meet the words, or that the repository does not define; the second level and below. `docs/local-check-cli.md`, *The code a reading turns on*.
- **The retrospective measurement is fixed before any case is examined** (#89, `bench/eval/RETRO.md`; protocol version 3). Real failure-handling defects a later pull request fixed, each paired with the pull request that put it in — named by the fix when that number is a pull request merged into the default branch before it, or else the pull request holding the most of the lines the fix removed, by `git blame -w -M -C` past whitespace-only commits (`retro/origin.ts`). The requirement is written from what existed when the original merged — its title, description, comments, reviews and issues as they stood then, read back through GitHub's edit history (`retro/material.ts`) — by an annotator run as `claude -p` with no tools and a fixed prompt (`retro/prompts.ts`), checked by a second for anything only the fix could tell, and frozen before the tool runs. The gate: the lower bound of the detection rate above 0.20 over 17 repositories of this measurement's own sealed search, counting a case whose requirement could not be written as not detected, with guards on false findings and listed precision. A gap in the material — a version that cannot be read back, a list GitHub cut short — counts as a case without a requirement. September's search is recorded (`retro/search-v1.json`, 2026-09-01 to 09-23, titles only; a range where a phrase reached `gh search`'s silent limit of 100 is split until none does). `baseline.ts`'s `claudeArgs` takes a system prompt, its own call unchanged, and `assertEmptyDir` also refuses a directory inside a repository.
- **The frontier-model comparison is fixed before the sealed set is opened** (#88, ADR 0018; `bench/eval/BASELINE.md`). The baseline is Claude Opus 5.5 through `claude -p` with no tools, one request, in an empty directory with a fixed system prompt, no MCP server and no user settings, given the same requirement, diff and commit and material gathered by a fixed rule — the diff, the changed files, the files that call a changed function, the files the requirement's words hit — up to the bytes jev-intent-review sent on that version. A hit is the known defect's file, function and call in three runs of three, the same for both; both keep five findings. The gate is the lower bound of the per-case difference, repositories counted once, above 10 more defects per 100 cases, with a guard on false findings; at 17 repositories it needs 11 wins and no loss. The difference is read apart for defects inside the diff and in an unchanged caller, which the protocol now builds for every sealed repository: **`bench/eval/PROTOCOL.md` is version 2**, and its gates count both places. Nothing has been measured on sealed; on dev the baseline ran once on each of seven versions (`bench/eval/logs/baseline-dev-v0.json`, `-v1.json`). ADR 0017 is Accepted.

The first replay differs on 3.5 % (two pairs): `no_drift`, the same version, and the tool asks the same pairs it froze. - **Jev's drift on the dev set is measured against its own variation** (#87, `bench/eval/drift.ts`, rule in `bench/eval/drift/README.md`). `capture` freezes what the tool sends for every live dev case — each call's mapping and observation as one pair — by running it with a provider that records the questions and answers them itself, so nothing is sent; `baseline` sends every pair once per run, one request at a time in a new order, in batches on different days; `replay` sends them once more, takes the capture again to count pairs the tool no longer asks or asks newly, and compares in one command. - **What the listing of a function's calls silently drops, measured against a parser** (#81, `docs/call-oracle.md`, `bench/call-oracle/`, `bench/logs/call-oracle-dev.json`). A small Rust program built on `syn` lists the calls in each function, and every one is classified by what the listing did with it; every candidate the listing produced that is not a call is counted with its reason. On #80's dev cases (1,816 files of eight repositories) the listing drops 2,071 of 160,118 calls with nothing said (1.29%): every call with a turbofish on its last name (`foo::<T>(`, `.collect::<Vec<_>>()`, 1,143, none listed), 718 calls whose name the listing refuses as a macro's (`.write(buf)`), and calls below a string literal that continues at column 0, where the listing ends the function; and 26,876 of its candidates outside macros are not in-scope calls, 19,889 of them in test-only code. Nothing the tool does changes: the listing's calls carry a `column` the oracle pairs them by, which no report or request includes. The fixtures and their committed oracle output are checked by `npm test` without a Rust toolchain.

- **A requirement's section says how many of the calls that could be asked were read and how many were left, and the report's first line says what a run left** (#38). One line under the functions reached: read and answered, without an answer, held before their question, over the budgets, and how many more could not be asked — "All … were read and answered" only when that is everything. A call asked about and left without an answer (the request limit, the time, the host) is counted apart from those read and answered, so a run the request limit stopped no longer reads as complete. The first line adds how many calls were not checked, how many came back without an answer and how many notes say what the listing did not read (a cap, a file that could not be read, a search not followed), drawn from the same function as the Action's check run title, so the two say the same numbers. **The check run is green only when none of these is left** — a note on what was not read now keeps it neutral, which on a real repository is nearly every run. `--json` gains `unreached` per requirement: the notes that say something was not read.
- **A pull request template, and what to do about pull requests opened before one** (#42). `docs/writing-requirements.md` gives a `.github/pull_request_template.md` to copy beside the issue template, and says what happens to a pull request opened before either: it stops with exit 11 (*Requirements could not be read*, a red check), and is read once its description has a section — or `Closes #N` — and it is pushed to or its job re-run, since the tool reads the description from GitHub when the job runs; editing the description alone starts no run unless the workflow lists `edited`.
- **A limit for the whole pull request** (#42, ADR 0014). `limits.max_requests_per_pull_request` in `.jev-intent-review.yml` caps what the runs of one pull request send to Jev together, as far as the count carried in the Action's cache goes; a run that would go past it asks no more, and a note says what the pull request had sent, what the run could send and how many judgments it could not. Where `policy.fail_on` names `finding`, a run the limit left short — or that could not write its count and so sent nothing — exits 2 (1 when it listed a finding), so spending the limit cannot make a change pass unasked. It is counted in the `--answers` directory by the transport (`JevClient`'s `onRequest`), one line written just before each request leaves, a retry included — a request whose line cannot be written is not sent — and the value is read from the commit before the change. Without `--answers`, or where the count cannot be read privately, the notes say the limit was not applied. Unset, there is none. Not guaranteed: the count lives in the pull request's own cache and workflow, so its author can clear it or turn `remember-answers` off; one of several saves (overlapping runs, two jobs, a matrix) is lost; an evicted cache starts from 0; overlapping runs can pass it together, and whether a run cancelled by a later push saves its count before the next run restores the cache is not yet measured.
- **The local check reads the siblings of a change** (#37, ADR 0005): the other callers of the repository functions the changed code calls — the path a fix may have missed — which call nothing the change touched. A seed is a function here that the changed code calls, on a line it kept, added or removed, that returns a `Result` and is not a changed function (at most 8); a sibling is a function outside tests, not already read one hop out, with a call that settles at a seed, that returns a `Result`, and none of whose calls settles inside a changed function or, under a changed function's name, settles nowhere (at most 20). Which definition a call settles at, and whether it returns a `Result`, is the same reading that decides whether a call can be asked about: `applicabilityOf` is now `targetOf` and `calleeOf`, composed with every kind and reason unchanged. Siblings are asked last — after every requirement's calls and the changes' questions — under a budget of their own, 10 per requirement, the calls that tied them first; the first budget is the same set and is counted as before, and the siblings are counted apart (`counts.siblings` in `--json`, their own lines in the report). Their calls, and a finding in one, carry `origin: shares_call` and `via`. Seeds and siblings are chosen by returning a `Result` under either form (#39 for the other). - **A later push of the same pull request does not ask Jev again about what it already answered** (#42, ADR 0013). When the Action runs again on a pull request, a judgment whose evidence and questions are byte-identical to one already answered for that pull request is taken from that answer instead of being sent, and the report counts it as reused. The command does it with `--answers <dir>`: a private directory (0700) of keys and answers — the key is the SHA-256 of the host, the endpoint's origin, the model, the evidence packet and the questions' words, and the packet itself is never written there. It is read only after the run has found its credentials, so a run without them — a fork's pull request among them — is skipped as before and never reads it; a directory or file others can read is not used; a kept answer that no longer fits its question is asked again. Each answer is appended as it comes back, and two identical requests in flight in one run share one. The Action keeps the directory in the Actions cache (`actions/cache` pinned by commit, one key per run and job, restored by a prefix that names the pull request, saved when there is a ledger file; `remember-answers: false` turns it off). `--json` gains `sent.reused` and `sent.reusedFromEarlierRuns` (additive; still `version: 2`), and `sent.answered` keeps its meaning — what Jev answered in this run. A run answered entirely from kept answers is not "Nothing was asked"; a run that sent judgments and got no answer to any stops with exit 12 whatever it reused, and one its own budget ended does not count, as before. Not guaranteed, in `docs/local-check-cli.md`: whoever can write the pull request's cache is trusted — a same-repository author can plant answers with a workflow and remove the workflow in a later push; an evicted cache, a revoked key under a run answered entirely from the cache, a matrix's parallel legs, overlapping runs of one pull request. Measured on the 43 pushes of the 12 pull requests of ADR 0012, each run with and without kept answers against a stand-in whose answers follow each request (`bench/packet-reuse.ts --ledger`): the reused count, and the part of it kept from earlier runs, equal what the packets say should be covered on all 43, the reports read the same, and the median share of a later push answered from kept answers is 0.855. Each requirement's section names its form, and the labels of the function's answer are the form's. Still no requirement verdict, and a listed call still leaves the exit code at 0.
- An observation request that fails without ending the run (a malformed answer, a spent budget) now leaves that call *not settled* with the kind and the host, as a failed mapping request already did; before this it ended the whole run. A run that reached the host and got no answer at all fails with exit 12, naming the host when a failure carried its name, as the default review does; because a failure no longer ends the run at once, such a host is asked about each call inside the budget before that, bounded by `limits.max_requests`.
- Whether a call can be asked about is decided per requirement, not once per call: a form may read the requirement's words, so two requirements in one spec no longer share the first one's answer. Only "returns a `Result`", which depends on the commit alone, is decided once.

## [0.1.0] - 2026-09-21

### Added

- **An installable command.** `npm run build` emits JavaScript to `dist/`, `npm pack` makes a tarball that carries only that and the licences, and `jev-intent-review` runs from it without the source tree. `--experimental-local-check` is the v0.1 path: Rust, requirements that state how a failure must be handled, the functions a change touched and their callers one hop out. For each call it reaches it asks Jev, in two separate requests, whether the requirement requires that a failure of that call not reach the caller as a success, and what the function returns when it does fail; where both answers clear 0.6 and disagree, the call is listed with the requirement's words, the code, the assumed failure and both answers. You name no file, function or expected answer. Findings do not cause a nonzero exit code, and exit 0 does not establish that a requirement holds. Measured on one repository, two requirements, one run per branch: each of two mutations listed at its own call and nowhere else, and the shipped code and two behaviour-preserving rewrites listing nothing — ten cells of ten against a table fixed before the first request.
- Requirement verification from the command line. Intent comes from `--pr` (the issues a pull request closes, then its description, each with its author; outside a workflow, `--pr` also names the change: the commit the pull request started from and its head commit), `--issue`, `--intent`, `--intent-file`, or `--intent-spec` on its own. Requirements are read, not written: a spec file, or items listed under an "Acceptance criteria" style heading, taken as written (an item too short to check is listed as an ambiguity, not dropped). Anything else stops the run and names those two forms. For each requirement the tool searches the repository after the change — from every call the changed functions make, and from the words the change checks — and follows the callers of anything Jev calls a mere wrapper one hop further. It builds bounded, redacted evidence that includes how each place is reached and the bodies of what it calls, asks Jev whether each place is a path the requirement governs and whether it satisfies it, and reports a violation only when Jev both calls a place a path the requirement governs and says it fails there, each at `judgment.violation_probability` or above. VERIFIED covers the places Jev called paths of the requirement, all of them satisfied, with Jev judging the list of places likely complete and nothing the run could not judge (see Changed below for the rule this release settles on); otherwise UNKNOWN. With no credentials or no intent the run is skipped with exit 0, or fails, as `policy.missing_credentials` and `policy.no_intent` say.
- Changes no requirement asked for are reported. Every changed region that carries behaviour is judged against the requirements, and the ones Jev calls unasked-for, at `judgment.violation_probability` or above, are listed with the lines that changed. Comments, blank lines, imports and files with no code are left out before anything is asked; regions that were judged and are not shown are counted in a note, so "nothing to report" reads differently from "nothing was looked at". Which requirement would have asked for a change is not guessed, and no sentence about a change is generated. A test of what a requirement asks for, a helper or fixture such a test needs, and the comments on code that carrying a requirement out added, all count as part of carrying it out. Measured on the five real pull requests that had anything to report, with the same requirements and the same commits on both sides: 32 reports became 24, over an identical number of regions judged (20, 42, 86, 48 and 41), and a test written for an unasked-for change is still reported with it. Per pull request the change is not uniform — one went from 9 to 3, one from 6 to 7 — so part of this is the model's own spread. The report's `questionsHash` is `05f56019f295`; the wording before it hashed to `0e38233a1edf`.
- The endpoint for the judgments can be any HTTPS endpoint that serves Jev from a Workers AI run request: set `JEV_API_URL` and `JEV_API_TOKEN`. Without them it is Cloudflare Workers AI from `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`. Each token is sent only to the endpoint of its own pair, the URL comes from the environment and never from the configuration file, it must be `https:` (`http:` only for a loopback host) and carry no credentials, redirects are never followed, and the report names the endpoint's origin.
- The groundwork the command line stands on: it reads the change between two commits from git objects, never from the working tree's files or `.gitattributes`, and passes every diff setting explicitly so git config does not change what is read. It finds the function around each changed line and the calls made around it, loads `.jev-intent-review.yml` from the commit before the change, and renders the report as Markdown or JSON. The Jev client retries, and keeps a request, byte and time budget counted on what is actually sent; `npm run probe:jev` uses it to ask the real model.

### Changed

- **Only Jev is asked anything.** `CloudflareClient` refuses every other model before a request is built, so nothing leaves the process and nothing is counted as sent; the CLI and the bench scripts go through the same place. Three uses of a general instruct model are gone with it: the requirements are no longer written by a model — they come from `--intent-spec` or from an acceptance-criteria list read as written, and prose that is neither stops the run naming those two forms — the experimental path's call-picking model is removed, and whether a requirement governs a call is now Jev's own three-option answer with a probability, at the same bar as the reading of the code. Nothing in a report is model prose any more: a quote is the requirement as it was given, and the reasoning between the two answers is assembled from them.
- **VERIFIED is a claim about the paths Jev named, not about every place the search found.** A place counts towards a requirement only when Jev calls it a path of that requirement at `judgment.relevance_probability`; everything else — supporting, unrelated, or a path named too weakly — is set aside with its reason and counted, instead of leaving the requirement open. The section that reports a requirement now says what its status covers: how many places were judged of how many were found, how many were paths, how many were set aside, and which leads the search did not follow. Measured over 795 judged places on ten real pull requests, 19% were called paths at all (a median of 2 per requirement), and requiring every one of about 30 to come back decided left VERIFIED at 0 of 38 requirements. What the search left is now reported and handed to the completeness question rather than each item blocking on its own — all 38 carried at least one such reason, 405 in all. VERIFIED is still withheld outright for a path known by name and never judged, a run that stopped on its own budget, or a change to this tool's configuration or workflows. `NOT_APPLICABLE` is gone as a requirement status: with only paths deciding, it cannot be told apart from "no place it applies to was found". The report's `questionsHash` is `2dbfadbe52a2`; the wording before it hashed to `05f56019f295`.
- Evidence that was cut is read by which part was cut. The place's own code cut, or no block found for it at all, voids every answer about it, and the place is then counted with the ones the run could not judge — which withholds VERIFIED. Only its surroundings cut now voids a `violates` alone — the missing callers could hold the check, but they cannot remove a check that was seen — and surroundings that may belong to another definition of the same name void `satisfies` as well, including when the ambiguity is in a one-hop definition, which is where a guard usually lives. Of 116 cut packets measured across five pull requests, 111 had the place's own code whole. A packet built with no room for the surroundings at all says it was cut, instead of reporting nothing missing while showing none of them.
- The callers of code Jev calls a mere wrapper get room of their own instead of what the per-requirement cap has left. A requirement that filled the cap used to reach them with room for none: their names were known and not one was judged.
- A run that sent judgments and got no answer it could read exits 12 instead of reporting every place as unknown. A 404, a 405, a redirect, or a second unusable answer (refused, not JSON, or a failure the endpoint reports) while none has been read is taken as the endpoint rather than the request: the run stops as soon as one comes back, and nothing is sent after that, bar what was already in flight. A rate limit and a server error are never read that way. A run with no candidates, and a run that stops on its own request, byte or time budget, are unaffected and still report what they have.
- The endpoint's variables are read before anything else, so a malformed `CLOUDFLARE_ACCOUNT_ID` or `JEV_API_URL` exits 10 even on a run that would have been skipped for want of an intent.

### Fixed

- A test module behind a platform-qualified `cfg` is read as a test module: `#[cfg(all(test, unix))]` left the module looking like production code, so its helpers could be judged as places and the `fn`s it defines counted as definitions of names found elsewhere — which is what decides whether a name resolves to one definition or several. Only a predicate that cannot hold outside the tests is read that way. `any(test, feature = "…")` is compiled in an ordinary build with that feature on and is **not** a test region, and neither is `not(test)`, a feature whose name contains "test", or anything the reading does not recognise — code left in is visible, and code excluded is silently absent.
- `--pr` compares the commits the pull request changed. The base came from resolving the base branch by name, so for a pull request merged with a merge commit — where the branch has since come to contain the head — the merge base of the two was the head itself, and the tool reviewed a commit against itself: no changed files, no seeds for the search, and a report that said only that it found nothing, with no error. The base is now the latest commit the head still shares with one of the places it could be — the base branch, the branch as `origin` has it, and the base commit GitHub records for the pull request — which is right whether the branch has moved past the head, the head took the branch in later, or the clone's copy of the branch is behind. A run whose two commits are the same stops with exit 10 instead of reporting on an empty change. Measured on the ten pull requests of the first measurement: the five merged with a merge commit (sideeye) compare the commits the pull request changed, with the changed files matching GitHub's own list exactly, and the squash-merged ones (omamori) resolve to the same base as before.
