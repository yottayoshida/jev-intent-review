# Changelog

All notable changes to this project are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Removed

- **The generic run: repository-wide discovery, the relevance, satisfaction and completeness questions, and the verdict per requirement** (ADR 0007, replacing ADR 0002). `jev-intent-review` with no flag now does what `--experimental-local-check` did: the calls of the functions the change touched and their callers one hop out are read under each requirement's form, and each is reported as worth checking, holding, not settled or not required of. No VERIFIED, VIOLATION or UNKNOWN is stated anywhere. The flag is still accepted — the report and the exit code are the same without it, and one line on stderr says so; `--experimental-candidates-only` is `--candidates-only`, with the old name accepted. **In a language other than Rust no function is read and no call is asked about; only the change question runs** — the generic run had read any language. The benches that drove the generic run and the questions they sent are kept under `bench/generic/`, outside the type check, for the logs they produced.

### Changed (breaking)

- **`--json` is `version: 2`**, one shape for every way a run ends (skipped, stopped for want of readable requirements, `--candidates-only`, finished): `exitCode`, `skipReason` when skipped, `intent`, `sources`, `requirements` (the readings per call, as the local check printed them), `unexpectedChanges`, `sent` (`requests`, `bytes`, `answered` — the requests Jev answered, in the same unit as `requests` — and the endpoint and host) and `metadata`. Gone: `verdict`, `discovery`, and the per-requirement `status`, `coverage`, `scope` and `candidates`; a stopped run's separate `{revisions, sources, intent, notes}` shape, whose `notes` are now `metadata.notes`. Everything the generic run used to call a blocker or note beside the verdict — intent that exists and was not checked, a change to this tool's configuration or to a GitHub Actions workflow, requirements only from the pull request's own description, what the pass over the changes left out or redacted — is a note in `metadata.notes`, printed under `## Notes`. The Markdown report names its requirements' sections and the change question's; `Coverage` and the per-place lines are gone, `--candidates-only` says the set was built and nothing was asked, and `Sent to the judgment model` says how many requests were answered.
- **`policy.fail_on` defaults to `[]`, and its value is `finding`.** A call worth checking leaves the exit code at 0 unless the repository's `.jev-intent-review.yml` says `policy.fail_on: [finding]`, which exits 1 when any call is. A file that says `violation`, the value 0.1 knew, is read as `finding` and the notes say so. `policy.unknown`, `intent.pr_body_only: unknown`, `discovery.*`, `judgment.satisfaction_probability`, `judgment.relevance_probability` and `evidence.max_related_chars` no longer apply: a file that sets one is not refused, and the notes say which and why. They go in the next minor version.
- `metadata.questionsHash` now fingerprints what a run can send — the change question and the two forms' questions — where it used to cover the generic run's questions only.
- An observation request that fails, or a host that answers nothing usable over both the calls and the changes, is handled as before for the calls; a run whose only questions were the changes' (a repository the local check reads no function in) and got no answer now fails with exit 12 like any other.

### Added

- **A pull request template, and what to do about pull requests opened before one** (#42). `docs/writing-requirements.md` gives a `.github/pull_request_template.md` to copy beside the issue template, and says what happens to a pull request opened before either: it is skipped as having no requirement, and is read once its description has a section — or `Closes #N` — and it is pushed to or its job re-run, since the tool reads the description from GitHub when the job runs; editing the description alone starts no run unless the workflow lists `edited`.
- **A limit for the whole pull request** (#42, ADR 0014). `limits.max_requests_per_pull_request` in `.jev-intent-review.yml` caps what the runs of one pull request send to Jev together, as far as the count carried in the Action's cache goes; a run that would go past it asks no more, and a note says what the pull request had sent, what the run could send and how many judgments it could not. Where `policy.fail_on` names `finding`, a run the limit left short — or that could not write its count and so sent nothing — exits 2 (1 when it listed a finding), so spending the limit cannot make a change pass unasked. It is counted in the `--answers` directory by the transport (`JevClient`'s `onRequest`), one line written just before each request leaves, a retry included — a request whose line cannot be written is not sent — and the value is read from the commit before the change. Without `--answers`, or where the count cannot be read privately, the notes say the limit was not applied. Unset, there is none. Not guaranteed: the count lives in the pull request's own cache and workflow, so its author can clear it or turn `remember-answers` off; one of several saves (overlapping runs, two jobs, a matrix) is lost; an evicted cache starts from 0; overlapping runs can pass it together, and whether a run cancelled by a later push saves its count before the next run restores the cache is not yet measured.
- **The local check reads the siblings of a change** (#37, ADR 0005): the other callers of the repository functions the changed code calls — the path a fix may have missed — which call nothing the change touched. A seed is a function here that the changed code calls, on a line it kept, added or removed, that returns a `Result` and is not a changed function (at most 8); a sibling is a function outside tests, not already read one hop out, with a call that settles at a seed, that returns a `Result`, and none of whose calls settles inside a changed function or, under a changed function's name, settles nowhere (at most 20). Which definition a call settles at, and whether it returns a `Result`, is the same reading that decides whether a call can be asked about: `applicabilityOf` is now `targetOf` and `calleeOf`, composed with every kind and reason unchanged. Siblings are asked last — after every requirement's calls and the changes' questions — under a budget of their own, 10 per requirement, the calls that tied them first; the first budget is the same set and is counted as before, and the siblings are counted apart (`counts.siblings` in `--json`, their own lines in the report). Their calls, and a finding in one, carry `origin: shares_call` and `via`. Seeds and siblings are chosen by returning a `Result` under either form (#39 for the other). A sibling's calls left unasked are under *Not checked*, so the Action's check run can be neutral where it was green, and a finding in a sibling counts for `policy.fail_on`. A request cut off by the run's own deadline is now the run's time limit, not a host that did not answer, so a run with nothing answered yet keeps its report. Not yet measured on a case not used to tune anything.
- **A later push of the same pull request does not ask Jev again about what it already answered** (#42, ADR 0013). When the Action runs again on a pull request, a judgment whose evidence and questions are byte-identical to one already answered for that pull request is taken from that answer instead of being sent, and the report counts it as reused. The command does it with `--answers <dir>`: a private directory (0700) of keys and answers — the key is the SHA-256 of the host, the endpoint's origin, the model, the evidence packet and the questions' words, and the packet itself is never written there. It is read only after the run has found its credentials, so a run without them — a fork's pull request among them — is skipped as before and never reads it; a directory or file others can read is not used; a kept answer that no longer fits its question is asked again. Each answer is appended as it comes back, and two identical requests in flight in one run share one. The Action keeps the directory in the Actions cache (`actions/cache` pinned by commit, one key per run and job, restored by a prefix that names the pull request, saved when there is a ledger file; `remember-answers: false` turns it off). `--json` gains `sent.reused` and `sent.reusedFromEarlierRuns` (additive; still `version: 2`), and `sent.answered` keeps its meaning — what Jev answered in this run. A run answered entirely from kept answers is not "Nothing was asked"; a run that sent judgments and got no answer to any stops with exit 12 whatever it reused, and one its own budget ended does not count, as before. Not guaranteed, in `docs/local-check-cli.md`: whoever can write the pull request's cache is trusted — a same-repository author can plant answers with a workflow and remove the workflow in a later push; an evicted cache, a revoked key under a run answered entirely from the cache, a matrix's parallel legs, overlapping runs of one pull request. Measured on the 43 pushes of the 12 pull requests of ADR 0012, each run with and without kept answers against a stand-in whose answers follow each request (`bench/packet-reuse.ts --ledger`): the reused count, and the part of it kept from earlier runs, equal what the packets say should be covered on all 43, the reports read the same, and the median share of a later push answered from kept answers is 0.855. This repository's CI carries the answers from one job to the next through the cache against a stand-in endpoint (`bench/answers-roundtrip.ts`).
- **Jev chooses the form of a requirement read from an issue, a pull request, `--intent` or `--intent-file`** (ADR 0008). Before its calls, one typed question over the sentence alone — how a failure must propagate, that a check passes before an action, or neither — and the calls are read under the form Jev chose at the bar of 0.6; `neither`, a reading under the bar or no answer keeps the default, `failure_propagation`, as before. A spec's `form` is never asked; `--candidates-only` and a change that reached no function ask nothing and say so. The report's form line says who chose the form, and `--json` gains `formBy`, `formReading` and `formNotAsked` per requirement (additive; still `version: 2`). The question is the one measured on 72 sentences (`bench/forms/choice/`, `docs/local-check-cli.md`), held to the log's hash by a test; `metadata.questionsHash` covers it. A run over requirements read from text sends one more request per requirement.
- **A GitHub Action** (#41, ADR 0009): `uses: yottayoshida/jev-intent-review@<commit>` on a `pull_request` event runs the command once, at the Action's own ref, and leaves the report in a check run, the job summary and an artifact (`report.md`, `report.json`, the command's `stderr.txt`, and `action.json` with the ref and a hash of its `src`). The check run is green only when at least one call was read and nothing is worth checking, not checked or left without an answer; red when the command did not exit 0; neutral otherwise, so a run that checked nothing does not read as one that found nothing. Its findings are marked on their lines, through the Checks API, where the merge commit does not change the file. **Nothing the command, `npm ci` or the Action's own last step prints reaches the job log**: their output goes to files under `RUNNER_TEMP`, and what the Action adds to the log is a handful of fixed sentences — a requirement or a code excerpt cannot become a workflow command or a problem matcher's annotation. (The runner's own step headers and `env:` lines are still there, with a key from `secrets` shown as `***`.) Keys come from the Action's inputs and never from the job's environment, and every key and token is taken out of the artifact, the summary and the check run. `policy.missing_credentials` stays `skip` and is no longer provisional (ADR 0009). A documented way for a repository to hand the tool its requirements, and a budget per pull request, are still #42.
- **A pull request from another repository is not reviewed, and a run that asked nothing says which of four reasons it was** (#42, ADR 0010). The README's workflow — and this repository's own — runs its job only when the head repository is the repository, under a name that says so, so a fork's pull request shows a skipped job in the checks list instead of a green one that reviewed nothing; GitHub gives such a run no secrets, so there was never anything to review it with. The reason is decided once, in the command: the report carries `skipKind` (`fork`, `dependabot`, `no_credentials`, `no_intent`) beside the sentence, the check run's title switches on that value and not on the sentence's wording, and a value it does not know falls back to "see the job summary". Where that sentence can be read differs by case, and the README says so per case: a skipped job has only its name, a fork's or Dependabot's run cannot create a check run with the token it holds, and every other run gets the title as well as the job summary. Where a pull request came from is read from the event's head and base repositories, never from a repository's own fork flag — a pull request opened inside a fork, against that fork, is that fork's own, and a fork that has since been deleted, which GitHub leaves empty, is still another repository. `--json` gains `skipKind` and stays `version: 2`. The README says which pull requests are reviewed and which are not, and that fork pull requests cannot be.
- The README's workflow sets `concurrency` per pull request with `cancel-in-progress`, as this repository's own does, so a later push stops the earlier run and pushing several times in a row pays for the last push only (#42).
- `--skip-change-check`: read the calls and leave the changes unasked. The benches that measure the local check pass it, so what they record stays the local check's requests.
- **What another push would not have to ask again: measured, and the answer is most of it** (#42, ADR 0012). Nothing in the tool changes here. On 31 pairs of consecutive pushes from 12 real pull requests — every one of the acceptance set's 40 candidates attempted, and the 28 that could not be measured kept with the reason, 17 of them because they name issues of `yottayoshida/omamori` rather than pull requests — **the median share of a push's judgments whose packet was already answered at the push before it is 0.852**. One pull request carries 11 of the pairs; counted per pull request the share is 0.736, and every other way it was counted it stays above 0.50. The threshold for building a ledger was fixed at 0.50 before the numbers were taken, so the ledger is worth building and is the next change. Two things the numbers settle on the way: a packet that differs only in where its code sits is rare (blanking the line numbers moves the median to 0.869), and adding a requirement leaves the earlier ones' calls packets alone only when it goes last — the change question's packets change either way. A push is counted per commit, which puts the share above what a push carrying several commits would see. Taken with the tool at `0029a95`, before the table of functions outside the repository (ADR 0011). Asked of a stand-in endpoint on localhost, so nothing was billed; that the stand-in is sent what the real endpoint is sent is argued from the code, and measured on one pull request (13 of 13 packets the same, in a different order; `--fidelity`, log `bench/logs/fidelity-v1.json`); `bench/packet-reuse.ts`, log `bench/logs/packet-reuse-v1.json`, table in `docs/local-check-cli.md`.
- **How much a reading moves when the same packet is asked again: measured from records already taken** (ADR 0012). The acceptance bench runs every version three times over the same revisions, so each place was asked with byte-identical input three times: **the discrete reading differed between runs in 2 of 34 places, and both of them sit within 0.1 of the bar the tool decides on** (of the 34, 8 are pull request heads and 26 are versions built for the bench) (8 of the 102 readings do). In both, Jev chose the same answer every time and only its probability crossed the bar. Re-asking is itself unsteady at the bar, which is where a stored answer was supposed to be the risk; that reuse is no worse is inferred from this, not measured. `bench/answer-spread.ts`, log `bench/logs/answer-spread-v1.json`.

- **What the local check asks is a form, and one rule reads every form** (ADR 0006). A form is data — which calls can be asked about, the two typed questions, which answers go against the requirement and which keep it, the report's words — and `--experimental-local-check` reads every call it asked about with one rule, the same for every form, into worth checking / holding / not settled / not required of (`outcome` in `--json`: `violates` / `satisfies` / `unknown` / `aside`). `failure_propagation`, the default, is v0.1's questions and condition unchanged byte for byte (a test pins every request against a record taken before this change, and the 102 answer pairs of the #36 log read through the rule come out listed exactly where they were). `check_before_action`, set with `"form"` in a spec, asks whether the requirement requires a check to pass before a call and whether the function still makes the call in a case the requirement forbids it; it asks about calls whose name shares a word with the requirement or its `searchHints`, and not about calls into a function the run reads on its own. Measured on a constructed case only (`bench/forms/`); see `docs/local-check-cli.md`.

- **Jev through TypeSafe or Vercel AI Gateway, not only Cloudflare.** Set `JEV_PROVIDER` to `cloudflare`, `typesafe` or `vercel` and that host's key (`CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`, `TYPESAFE_API_KEY`, or `AI_GATEWAY_API_KEY`), and every judgment goes in that host's documented request form to that host's fixed URL, and to no other. Before this, `JEV_API_URL` could only reach an endpoint that speaks Workers AI's run request, which TypeSafe and Vercel do not, so their users could not use the tool. Only Cloudflare has been called for real; the TypeSafe and Vercel requests follow their documentation and are tested against a stand-in. See ADR 0003.

- **Requirements read from the issue and the pull request as their authors wrote them.** Two documented forms are read, with no model writing or choosing anything (ADR 0004, `docs/writing-requirements.md`): the items of a requirements section — `Acceptance criteria`, and now also `Acceptance`, `Requirements`, `Definition of done`, `Done when` — and a paragraph that begins `Property:` (or `**Property** —`, `Property —`, `Property (…):`). Each source is read on its own: before this, one source in prose meant nothing was read from any, and on the ten measured pull requests and omamori #476 nothing was (0 of 11); now 7 of the 10 are. Every source that is not read is named with the reason, in an Intent section of every report and of the local check's output, and in `intent.ambiguities` of the JSON; the Intent section also shows each requirement as it was read. Left out of what is read, and only these: HTML comments, code blocks, link reference definitions, and characters that display as nothing (zero-width and direction-control characters, tag characters, variation selectors). The reading follows the page: a `<!--` inside code is text, an item includes the paragraphs indented under it, and a deeper heading inside a requirements section continues it.
- `docs/writing-requirements.md`, with an issue template to copy.
- **Choosing requirement sentences out of prose: measured, and not adopted** (#40). On 491 sentences of 64 issues people wrote in six Rust projects in 2019–2022, labelled before Jev was asked by three Claude annotators at the maintainer's request (not by a person, and shown more than Jev was: each sentence's id, for most, other sentences of its issue, and the maintainer's workspace instructions — see the docs), Jev chose the sentences that state a required behaviour with a precision of 0.82–0.85 and a recall of 0.91–0.94 per run. Precision neither cleared the 0.80 fixed beforehand nor fell below it — its 95% bounds were 0.70–0.73 and 0.89–0.92 — which the rule fixed before the labels takes as not adopting: prose is still not read as requirements. A rule on headings and "should/must" scored 0.46. The bench, its record and the table are in `bench/sentence-choice/` and `docs/writing-requirements.md`; the tool's behaviour does not change.

### Changed

- **The acceptance set measured again after `#45`** (`docs/local-check-cli.md`, *The acceptance set after `#45`*; `bench/logs/acceptance-v2.json`, 708 requests over 27 runs, both cases now marked as used to tune). Inside the diff both cases read as before, three of three. moltis#1064's defect in an unchanged caller, held before any question in the first measurement, was listed at its own call in three runs of three, and not listed on the shipped code. Without a request, a fixed call is inside the budget in 8 of 11 candidates, where it was 3 before `#45`; Kontor#385's unchanged caller's call can be asked about and is outside the budget (`#38`). A measurement's log now records each case's role as it was, and the table of the first measurement is rebuilt unchanged.
- **In the local check, whether a function returns a `Result` is read from its whole signature and the repository's aliases, and "does not return a Result" is said only when that was settled.** The return type is read past the generics and parameters up to the body (it used to be four lines of the callee, eight of the function), and a `use … Result as X` rename or a `type X = …` alias defined in the repository is followed, so `ChannelResult<T>`, `CostResult<T, E>` and a return type on the fifth line count. A callee is found as the one `fn <name>` outside tests, comments and strings — a JavaScript function, a `let` line or a Markdown snippet no longer counts, a name as common as `get` is no longer cut at 200 hits into "one definition", and `fn new` is found — and a call that cannot reach it (a method call to a function that takes no `self`, or a number of arguments it does not take) is held as having no definition here. A type from a dependency, `Self`, a type parameter or an alias that disagrees is reported as not settled (`target_return_unknown` / `callee_return_unknown`), with what could not be read, instead of "does not return a Result"; either way the call is not asked about. On 13 pre-check runs 98 calls became askable and 9 were held, scored against labels written by hand beforehand with no unexplained disagreement (`docs/local-check-cli.md`, *Reading whole signatures*).
- **In the local check, a call into a function this repository does not define can be asked about when it writes a path this tool knows** (ADR 0011). One table holds functions of the standard library and of `serde_json` whose return type is a `Result` — `fs::read_to_string`, `File::open`, `env::current_dir`, `serde_json::to_string_pretty` and 57 more — and a call is matched on the path it writes, by its ending: `fs::rename(a, b)` and `std::fs::rename(a, b)` both match the row `fs::rename`. Four rows are matched only in full (`std::env::var`, `std::io::copy`, `std::io::read_to_string`, `fs::File::metadata`), because the shorter ending means something else in a crate that exists. **A method call is never matched**: Rust resolves a method by its receiver's type, which this does not read, and `entry.file_type()` is `io::Result<FileType>` on a `DirEntry` and a plain `FileType` on a `Metadata`. `crate::`, `self::` and `super::` are left to this repository's own definitions, and a path written `std::` is answered by the table before them. Every row is there because `bench/outside-results-check.ts` read the standard library's source and a machine's cargo registry — 553 definitions a call could reach that way — and found none returning anything else. On 15 runs 40 calls became askable, none stopped being askable, and instruckt-tauri#9's fixed call is inside the budget; pybun#428's `entry.file_type()` is not opened (`docs/local-check-cli.md`, *Functions this repository does not define* and *Functions outside the repository*). With more calls askable, the order inside a function (below) now swaps calls in five functions on every branch of omamori `#468`, eight of Kontor#385 and one of pybun#428, and Kontor#385's fixed call is inside the budget only because of it (*The order inside a function*).
- **In the local check, a callee whose name this repository defines more than once can be settled instead of held.** Three things narrow it: the path the call writes (`SyncState::load_strict(root)` keeps the definitions under `impl SyncState`, `Self::path(root)` those under the `impl` the call is in, `install::add_package(args)` those in `install.rs`), the form of the call (a method call reaches nothing that takes no `self`, and nothing taking a different number of arguments), and definitions that are versions of one thing — a trait's method whose declaration is in this repository, or a function written once per platform under `#[cfg(…)]` at the top of one file — where every version must return a `Result`. Past 20 definitions after the path, their signatures are not read. **A path that matches none of the definitions is held, not reported as having no definition**: a type brought in under another name (`use … Error as ChannelError`) and a function re-exported from another file are definitions this does not follow. Definitions in a file declared `#[cfg(test)] mod x;` no longer count as a callee's, because no shipped code reaches them; a name whose definitions are all there is held with that as its reason, where it used to be read as if it were code. On 15 runs — the 13 of the pre-check and the two pull requests whose fix this was built on — 45 calls became askable, none stopped being askable, and three of the four fixed calls of cce-rust#168 and dataprof#370 are inside the budget of 20 (the fourth, `KnowledgeSyncState::load_strict`, is askable and outside it) (`docs/local-check-cli.md`, *Names defined more than once*).
- **In the local check, a function's calls into a function the change touched are asked first.** The budget of 20 is still dealt one call per function at a time, functions in the same order; inside each, the askable calls whose callee resolved to a changed function's definition now come before the others, which keep their line order. Only the `failure_propagation` form resolves callees; under `check_before_action` the order is line order, as before. When a function gets fewer questions than it has askable calls, that decides which calls are asked, and the order of the calls asked — `wouldAsk`, `observed`, `mappings`, `findings` and the over-budget part of `unchecked` in `--json`, and the report's lists — follows it. The evidence for this order is one case, Kontor#385, and it is the case the order was chosen from; the opposite shape (a defect beside a call into a changed function) is untested. On omamori `#468` the order swaps one call for another in one function on every branch; both were asked of Jev three times on every branch and neither was listed. On Kontor#385 it swaps calls in three functions, and those were not asked. These counts are from when the order was merged; the entry above says what the table of outside functions made of them (`docs/local-check-cli.md`, *The order inside a function*).
- **A requirements list item that wraps onto a second line is read whole.** It used to be cut after its first line, and the items after it were lost without a word.
- **A requirement over 600 characters is left out, and said to be, instead of being cut.** Input that used to run on a truncated requirement can now read nothing and stop with exit 11.
- **Reading the intent happens before the credentials gate.** A run without credentials is still skipped (exit 0), and its report now says what would have been read and what was not. With credentials, a run that reads nothing stops with exit 11 and prints, on stdout, the same Intent section (with `--json`: `revisions`, `sources`, `intent` and `notes`); stderr names each source and why. Intent given with `--intent` or `--intent-file` that cannot be read stops the run even when another source could be read.
- **Where each requirement came from is shown**, including whether its source's author is the pull request's (the local check's JSON gains `sources` and `intent`). In the review as it was then (retired in the same unreleased version; see *Removed*), intent that exists and was not checked was a blocker, which withheld VERIFIED — it is a note in `metadata.notes` now: a source that no source read outranks and that was not itself read (an issue in prose beside a pull request whose `Property` was read, or beside another issue whose list was), requirements past the first twenty, and issues the pull request closes past the ten GitHub lists; `intent.pr_body_only` looks at where the requirements were read from; and requirements read from the pull request's own description are not used to judge whether a change was asked for — when that leaves none, that check is not run, and the report says so.
- `--experimental-candidates-only` takes requirements from the forms as well as from `--intent-spec`; it still asks no model. An `--intent-spec` that lists no requirement now stops it with exit 11, as it already stopped every other path, and the message names the file.
- A pull request that closes an issue in another repository (`Fixes owner/repo#12`) no longer has that issue read as this repository's `#12`; it is named instead, with or without a token, and so are issues past the ten GitHub lists — in every report, in a stopped or skipped run, and in the local check's output. Without a token, closing keywords inside comments and code blocks are no longer followed.
- In the local check's Markdown, the requirement and its quote are shown as code spans, so no text from an issue or pull request can start a heading, a comment or a line of its own.
- Notes in the report escape backslashes and show `www.` addresses as code, so a quoted item cannot form a link.
- Without `JEV_PROVIDER`, selection is as before: `JEV_API_URL` with `JEV_API_TOKEN`, else the Cloudflare pair. `TYPESAFE_API_KEY` or `AI_GATEWAY_API_KEY` alone selects nothing, so a key kept in the environment for something else does not start sending code. `JEV_PROVIDER` with a value that names no host, or together with `JEV_API_URL`, is a configuration error (exit 10); with the named host's key missing, the run has no credentials whatever other hosts' keys are set, and the skip says which variable that host needs.
- Every failure that comes back from a host names the host and its origin — `TypeSafe (https://api.typesafe.ai) answered 422: …` — including an answer of the wrong shape, which before this did not say where it came from. In the experimental local check, a mapping question that failed is recorded as `not answered (<kind> from <host>)` instead of a bare "not answered", and a failure that ends the run (a refused key, an empty balance, a wrong endpoint) or a fault in this tool now ends it at that question instead of being counted as unanswered.
- An answer's probability for its choice is checked to be a finite number from 0 to 1 — `probabilities[choice]` when given, else `confidence` — and so is every kept probability. Before this only `confidence` was checked, while decisions read `probabilities[choice]` first, so `{"yes": 60}` passed and was read as 60. `confidence` is now optional, and `null` counts as absent; the JSON report carries the checked value as `probability` on each answer and may leave `confidence` out. All 840 choice answers kept in the saved bench logs — as the previous check stored them, not as Cloudflare sent them — pass the new check.
- The report's endpoint line names the host, and the warning at the top appears for an endpoint set by `JEV_API_URL` (decided by how it was chosen, not by its origin) instead of for anything other than Cloudflare. `sent.host` is added to the JSON report.
- TypeSafe's 529 ("overloaded") is retried like 429 and 5xx.
- `JevClient` (was `CloudflareClient`, in `src/judgments/client.ts`, was `cloudflare.ts`).
- **v0.1 measured on cases it was not tuned on.** Forty merged pull requests from other repositories were examined in a fixed order for a requirement about how a failure must be handled and a fix v0.1 can put a question to; twelve had such a requirement, three had a fixed call a question could be put to, and two could be built and run to observe a defect: moltis-org/moltis#1064 and dashpay/grovedb#500 (`bench/acceptance/`). Inside the diff both were read right in three runs of three: each defect listed at its own call, the shipped code and a behaviour-preserving rewrite listing nothing. No question reached a defect placed outside the diff, and in all three candidates whose fixed call could be asked, the call from the unchanged caller to the changed function was stopped before a question — by a `Result` alias, a callee signature wrapped past the four lines v0.1 reads, and a per-function cap (in grovedb#500 the caller itself was reached and other calls in it were asked about; in the other two every call in it was held). At forty candidates two had passed, and the owner chose to measure them rather than stop. With the decision moved into a helper whose body is not sent, Jev still answered with confidence (0.92–0.96). `docs/local-check-cli.md` now reports this beside the omamori case v0.1 was tuned on, and its tables are rebuilt from the committed log by `node bench/acceptance/replay.ts`, checked byte for byte by a test.
- The README's example no longer says the tool can surface a defect in an unchanged caller: in v0.1 that is a goal, and the measurement above found no call from such a caller to the changed function reaching a question.
- The local check's report: "Read as required by the requirement" is gone, split into *Worth checking*, *Read as holding* and *Not settled*; "Read, but not required of by the requirement" now holds only `does_not_apply` over the bar (the `unknown`, under-the-bar and unanswered mappings it used to hold are under *Not settled*). Each requirement's section names its form, and the labels of the function's answer are the form's. Still no requirement verdict, and a listed call still leaves the exit code at 0.
- An observation request that fails without ending the run (a malformed answer, a spent budget) now leaves that call *not settled* with the kind and the host, as a failed mapping request already did; before this it ended the whole run. A run that reached the host and got no answer at all fails with exit 12, naming the host when a failure carried its name, as the default review does; because a failure no longer ends the run at once, such a host is asked about each call inside the budget before that, bounded by `limits.max_requests`.
- Whether a call can be asked about is decided per requirement, not once per call: a form may read the requirement's words, so two requirements in one spec no longer share the first one's answer. Only "returns a `Result`", which depends on the commit alone, is decided once.

## [0.1.0] - 2026-09-21

### Added

- **An installable command.** `npm run build` emits JavaScript to `dist/`, `npm pack` makes a tarball that carries only that and the licences, and `jev-intent-review` runs from it without the source tree. `--experimental-local-check` is the v0.1 path: Rust, requirements that state how a failure must be handled, the functions a change touched and their callers one hop out. For each call it reaches it asks Jev, in two separate requests, whether the requirement requires that a failure of that call not reach the caller as a success, and what the function returns when it does fail; where both answers clear 0.6 and disagree, the call is listed with the requirement's words, the code, the assumed failure and both answers. You name no file, function or expected answer. Findings do not cause a nonzero exit code, and exit 0 does not establish that a requirement holds. Measured on one repository, two requirements, one run per branch: each of two mutations listed at its own call and nowhere else, and the shipped code and two behaviour-preserving rewrites listing nothing — ten cells of ten against a table fixed before the first request.
- Requirement verification from the command line. Intent comes from `--pr` (the issues a pull request closes, then its description, each with its author; outside a workflow, `--pr` also names the change: the commit the pull request started from and its head commit), `--issue`, `--intent`, `--intent-file`, or `--intent-spec` on its own. Requirements are read, not written: a spec file, or items listed under an "Acceptance criteria" style heading, taken as written (an item too short to check is listed as an ambiguity, not dropped). Anything else stops the run and names those two forms. For each requirement the tool searches the repository after the change — from every call the changed functions make, and from the words the change checks — and follows the callers of anything Jev calls a mere wrapper one hop further. It builds bounded, redacted evidence that includes how each place is reached and the bodies of what it calls, asks Jev whether each place is a path the requirement governs and whether it satisfies it, and reports a violation only when Jev both calls a place a path the requirement governs and says it fails there, each at `judgment.violation_probability` or above. VERIFIED covers the places Jev called paths of the requirement, all of them satisfied, with Jev judging the list of places likely complete and nothing the run could not judge (see Changed below for the rule this release settles on); otherwise UNKNOWN. With no credentials or no intent the run is skipped with exit 0, or fails, as `policy.missing_credentials` and `policy.no_intent` say.
- Changes no requirement asked for are reported. Every changed region that carries behaviour is judged against the requirements, and the ones Jev calls unasked-for, at `judgment.violation_probability` or above, are listed with the lines that changed. Comments, blank lines, imports and files with no code are left out before anything is asked; regions that were judged and are not shown are counted in a note, so "nothing to report" reads differently from "nothing was looked at". Which requirement would have asked for a change is not guessed, and no sentence about a change is generated. A test of what a requirement asks for, a helper or fixture such a test needs, and the comments on code that carrying a requirement out added, all count as part of carrying it out. Measured on the five real pull requests that had anything to report, with the same requirements and the same commits on both sides: 32 reports became 24, over an identical number of regions judged (20, 42, 86, 48 and 41), and a test written for an unasked-for change is still reported with it. Per pull request the change is not uniform — one went from 9 to 3, one from 6 to 7 — so part of this is the model's own spread. The report's `questionsHash` is `05f56019f295`; the wording before it hashed to `0e38233a1edf`.
- The endpoint for the judgments can be any HTTPS endpoint that serves Jev from a Workers AI run request: set `JEV_API_URL` and `JEV_API_TOKEN`. Without them it is Cloudflare Workers AI from `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`. Each token is sent only to the endpoint of its own pair, the URL comes from the environment and never from the configuration file, it must be `https:` (`http:` only for a loopback host) and carry no credentials, redirects are never followed, and the report names the endpoint's origin.
- The groundwork the command line stands on: it reads the change between two commits from git objects, never from the working tree's files or `.gitattributes`, and passes every diff setting explicitly so git config does not change what is read. It finds the function around each changed line and the calls made around it, loads `.jev-intent-review.yml` from the commit before the change, and renders the report as Markdown or JSON. The Jev client retries, and keeps a request, byte and time budget counted on what is actually sent; `npm run probe:jev` uses it to ask the real model.

### Changed

- **Only Jev is asked anything.** `CloudflareClient` refuses every other model before a request is built, so nothing leaves the process and nothing is counted as sent; the CLI and the bench scripts go through the same place. Three uses of a general instruct model are gone with it: the requirements are no longer written by a model — they come from `--intent-spec` or from an acceptance-criteria list read as written, and prose that is neither stops the run naming those two forms — the experimental path's call-picking model is removed, and whether a requirement governs a call is now Jev's own three-option answer with a probability, at the same bar as the reading of the code. Nothing in a report is model prose any more: a quote is the requirement as it was given, and the reasoning between the two answers is assembled from them.
- **VERIFIED is a claim about the paths Jev named, not about every place the search found.** A place counts towards a requirement only when Jev calls it a path of that requirement at `judgment.relevance_probability`; everything else — supporting, unrelated, or a path named too weakly — is set aside with its reason and counted, instead of leaving the requirement open. The section that reports a requirement now says what its status covers: how many places were judged of how many were found, how many were paths, how many were set aside, and which leads the search did not follow. Measured over 795 judged places on ten real pull requests, 19% were called paths at all (a median of 2 per requirement), and requiring every one of about 30 to come back decided left VERIFIED at 0 of 38 requirements. What the search left is now reported and handed to the completeness question rather than each item blocking on its own — all 38 carried at least one such reason, 405 in all. VERIFIED is still withheld outright for a path known by name and never judged, a run that stopped on its own budget, or a change to this tool's configuration or workflows. `NOT_APPLICABLE` is gone as a requirement status: with only paths deciding, it cannot be told apart from "no place it applies to was found". The report's `questionsHash` is `2dbfadbe52a2`; the wording before it hashed to `05f56019f295`.
- Evidence that was cut is read by which part was cut. The place's own code cut, or no block found for it at all, voids every answer about it, and the place is then counted with the ones the run could not judge — which withholds VERIFIED. Only its surroundings cut now voids a `violates` alone — the missing callers could hold the check, but they cannot remove a check that was seen — and surroundings that may belong to another definition of the same name void `satisfies` as well, including when the ambiguity is in a one-hop definition, which is where a guard usually lives. Of 116 cut packets measured across five pull requests, 111 had the place's own code whole. A packet built with no room for the surroundings at all says it was cut, instead of reporting nothing missing while showing none of them.
- The callers of code Jev calls a mere wrapper get room of their own instead of what the per-requirement cap has left. A requirement that filled the cap used to reach them with room for none: their names were known and not one was judged.
- A run that sent judgments and got no answer it could read exits 12 instead of reporting every place as unknown. A 404, a 405, a redirect, or a second unusable answer (refused, not JSON, or a failure the endpoint reports) while none has been read is taken as the endpoint rather than the request: the run stops as soon as one comes back, and nothing is sent after that, bar what was already in flight. A rate limit and a server error are never read that way. A run with no candidates, and a run that stops on its own request, byte or time budget, are unaffected and still report what they have.
- The endpoint's variables are read before anything else, so a malformed `CLOUDFLARE_ACCOUNT_ID` or `JEV_API_URL` exits 10 even on a run that would have been skipped for want of an intent.

### Fixed

- A test module behind a platform-qualified `cfg` is read as a test module: `#[cfg(all(test, unix))]` left the module looking like production code, so its helpers could be judged as places and the `fn`s it defines counted as definitions of names found elsewhere — which is what decides whether a name resolves to one definition or several. Only a predicate that cannot hold outside the tests is read that way. `any(test, feature = "…")` is compiled in an ordinary build with that feature on and is **not** a test region, and neither is `not(test)`, a feature whose name contains "test", or anything the reading does not recognise — code left in is visible, and code excluded is silently absent.
- `--pr` compares the commits the pull request changed. The base came from resolving the base branch by name, so for a pull request merged with a merge commit — where the branch has since come to contain the head — the merge base of the two was the head itself, and the tool reviewed a commit against itself: no changed files, no seeds for the search, and a report that said only that it found nothing, with no error. The base is now the latest commit the head still shares with one of the places it could be — the base branch, the branch as `origin` has it, and the base commit GitHub records for the pull request — which is right whether the branch has moved past the head, the head took the branch in later, or the clone's copy of the branch is behind. A run whose two commits are the same stops with exit 10 instead of reporting on an empty change. Measured on the ten pull requests of the first measurement: the five merged with a merge commit (sideeye) compare the commits the pull request changed, with the changed files matching GitHub's own list exactly, and the squash-merged ones (omamori) resolve to the same base as before.
