# 0012. What reusing an answer across pushes would save is measured before a ledger is built

Status: Accepted

## Context

`synchronize` fires on every push, so a pull request pays for a full run each time. Issue #42 proposes a ledger: keep the answers for a pull request and send no second request for a packet byte-identical to one already answered, keyed on the packet's hash together with `questionsHash`.

Two things about that proposal were unknown, and both decide whether it is worth building.

**What it would save.** The packet a run sends carries `candidate.lines` — the function's start and end line — so a push that inserts a line above a function changes that function's packet even when the function itself does not change. Nobody has counted how much of a pull request's evidence survives a push unchanged. The repository has no record of a pull request's consecutive pushes to count it from: `bench/acceptance/cases/*/case.json` holds one `prHead` per pull request and synthetic patch versions, not the pushes people made.

**What it would change.** #42 states the risk itself: "Jev's spread from run to run has not been measured (#36), so a cached answer may be one draw, not the answer." A stored answer would freeze one draw, and near the bar the tool decides on (`BAR = 0.6`, `src/plan/local-check.ts`) a different draw can change what the report says.

An adversarial review of the plan that built the ledger first found three more obstacles that only matter once it exists: a run whose answers all came from the ledger sends nothing, so `nothingSent()` (`src/report/markdown.ts`) reads it as a run that asked nothing and the Action titles it "Nothing was asked"; `actions/cache` entries are immutable, so a key fixed per pull request would freeze the ledger at the first push; and `sent.answered` is defined in the same unit as `sent.requests`, which reuse would break.

## Decision

- **Measure both before building anything.** This change adds no mechanism to the tool. `src/` is not touched.
- **The spread is measured from records already paid for.** `bench/logs/acceptance-v1.json` holds three runs of each acceptance version over the same `(base, head)`, so every place was asked the same question about the same packet three times. Counted per place from `requirements[].observed[]`: **34 places, three runs each; the discrete reading differed between runs in 2 of them; 8 of the 102 readings sit within 0.1 of the bar, and both places that differed are among them.**
  - Not counted from `sent[].packet`: that hash is per requirement × candidate *function*, so several calls in one function share it. Counting there gives 12, which is an artefact of the collapse.
  - In both places Jev chose `returns_success` every time; its probability moved between 0.57 and 0.68, and `describe` (`src/plan/local-check.ts`) reports a reading below the bar as `cannot_determine`. That a place which differs sits at the bar follows from how the bar works, so the count says how often a probability sits there, not that Jev changes its mind.
- **What that means for reuse — an inference, not a measurement.** Asking the same packet again is itself unstable near the bar. So "a stored answer is one draw" is a worry that assumes re-asking is stable, and it is not. We therefore take **reuse to be no worse than re-asking**, and steadier, because the report stops changing between pushes for reasons that are not in the code. Nothing here measured a report built from stored answers; the direction was fixed in the plan before the count was taken.
- **What it would save is measured on pull requests that exist**, from their commits (`/repos/{owner}/{repo}/pulls/{n}/commits`), not on a push sequence written for the occasion. Judgments are asked of a stand-in endpoint on localhost, so the measurement costs nothing: the packets a run sends do not depend on the answers it gets — `selectSites` finishes before the first request and `applicabilityOf` asks no model, and the observation question is sent whatever the mapping question answered.
- **The threshold was fixed before the numbers were seen**: on the share of a push's judgments whose packet is byte-identical to one already answered for that pull request, median over the measured pairs — at or above 50% the ledger is built; below 50%, but at or above 50% once packets that differ only in their line numbers are included, the key's definition is what is worth changing and that is a separate decision; below that, the ledger is not built and #42's item is recorded as not filed.
- **Measured: 0.852** over 31 pairs from 12 pull requests, every one of the acceptance set's 40 candidates having been attempted (`docs/local-check-cli.md`, *What another push would not have to ask again*). One pull request carries 11 of the pairs; counted per pull request (0.736), without it (0.736), pooled (0.806) or on each pull request's first pair only (0.616), the share is lower and still above 0.50. **The ledger is worth building**, and that is the next change, not this one.
- **The key stays the packet as it is sent.** Blanking the line numbers before comparing moves the median from 0.852 to 0.869. The line numbers a packet carries were the reason to expect little reuse, and they are not what decides it; a key that ignored them would buy about two points and would have to say what "the same evidence" means when the evidence sits somewhere else.
- **A requirement is added last, or the pull request pays for it** — on the calls' side. A packet holds one requirement, so appending one leaves the earlier requirements' packets as they were; putting one in front renumbers every id a packet carries and none of them matches. The change question's state holds all of them at once and changes either way. Whoever builds the ledger states this where the requirement forms are documented, rather than making the ids content-derived, which would change what every report shows.

## Alternatives considered

- **Build the ledger now and measure afterwards.** The reviews found the failure above (`nothingSent`) would make a fully reused run read as a run that checked nothing — the reading #42 exists to remove — and a structural limit nobody had counted. Building first risks shipping a mechanism that works and saves nothing.
- **Measure with a push sequence written for this purpose.** It would measure how this repository's author edits code, not how contributors push.
- **Measure by running the real endpoint over five pushes.** About 380 requests for a number a stand-in gives for nothing.
- **Take the eight acceptance branches' agreement (3/3 in each) as the answer on spread.** Those probabilities are 0.89–1.00, far from the bar; they say nothing about the places where a different draw changes the report. Counting per place instead of per branch is what surfaced the two that differ, and both are at the bar.

## Consequences

- #42 stays open. This settles that its ledger item is worth doing; the item itself is the next change, and the obstacles under Context are its work: the result line must stop reading `sent.requests` alone, the cache key must not be fixed per pull request, and `sent.answered` must keep its unit.
- Every number was taken with the tool at `0029a95`, before ADR 0011's table of functions outside the repository was merged. That table changes which calls are asked about, so the ledger's plan measures again on the tool it is built into rather than reusing these.
- The population is stated beside every number. 17 of the 40 candidates are not pull requests — they name issues of `yottayoshida/omamori`, another repository by this tool's author — so no pull request of the author's own is measured here, and 11 more have a single commit. A pair is counted only when both of its runs exited 0; none was left out. The spread count covers 34 places in the acceptance cases, of which 8 are pull request heads and 26 are versions built for the bench; one of the two that differed is a `hidden` version, built to sit below the bar.
- What is still unmeasured: how a pull request's pushes are spread over time, and therefore whether a cache would still hold the earlier answers when the later push runs. A ledger that misses is a ledger that saves nothing, and this says nothing about how often it would miss. And a push is counted per commit: a push that carries several commits changes more, so the share per real push would be lower than the one measured.
- A measurement taken against a stand-in is worth what its fidelity is worth. The packets are argued to be answer-independent from the code, and **measured on one pull request**: on `oxidezap/whatsapp-rust#759` at its head, the stand-in and Jev (Cloudflare) were sent the same 13 packets, each once (`bench/logs/fidelity-v1.json`). `bench/packet-reuse.ts --fidelity` compares them as a multiset, because the change questions go out together and the trace's order follows which answer came back first — and the order did differ. The other eleven pull requests rest on the argument.
