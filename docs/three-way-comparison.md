3 方式を同じコード・同じ条件で比べた。

| 方式 | 中身 |

## 送信前に分かったこと: 凍結した問いが当たらなかった

`docs/frozen-spec-v1.md` は v4 を凍結した。**新しい 2 件は、1 要求も送る前にそれを壊した。**
v4 のテンプレートは `… returns … at one iteration` と `finite` 欄を持つ——**iterator の形**が
埋め込まれている。新しい対象はどちらも 1 回の呼び出し（`read_to_string_capped(&path, …)?`）で
失敗するので、反復が無い。

**凍結した問いは、最初に出会った新しい失敗伝播の種類に travel しなかった。** 出現の仕方
（`occurrence`）と追加条件（`extra`）をデータに出した **v5**（`bench/check-questions-v5.ts`）を
作った。選択肢・`MEANING`・判定規則・閾値・v4 が足した 3 点はそのまま。**v4 の数字は v5 の
数字ではない**ので、v4 が終了条件を満たしたケースを v5 で測り直した——`staging_info_from` の
出荷版 3/3・変異版 3/3 で、v5 でも成立する。

## 訂正（2026-09-21、この文書の初版に対して）

初版は B の失敗を 4 点に数え、そのうち「必要な参照先が `[]`」を止まる直接原因と書いた。
**そこが誤り。** 測って直した。

**① 参照先は要らなかった。** PR #18 の条件は *iterator* が `Err` を返すと仮定していたので、
その間に立つ `collect_listing` の挙動が要った。**今回の条件は `read_to_string_capped(…)`
自身が `Err(io_error)` を返すと仮定している**——呼び先の結果を既に置いているので、対象の
`?` や `else { return Ok(None) }` を読めば答えは決まる。

実測（`bench/logs/referent-needed-v1.json`、12 要求）: 参照先を packet から外して
**4 セルとも 3/3、確率 0.98-1.00**——入れていた時（0.94-0.99）より高い。
**人の計画が要らない参照先を宣言し、実行器の「`[]` なら一律停止」がそれより強い制約だった。**
B は参照先を挙げなかったことでは間違っていない。

**② B が走ったらどうなるかを測っていなかった。** 停止を外して、保存した B の計画を
そのまま再生した（`bench/logs/b-replay-v1.json`、12 要求。生成し直していないので文面は同一）:

| ケース | B の対象 | 出荷版 | 変異版 |
|---|---|---|---|
| `read_baseline` | `read_to_string_capped`（`atomic_file.rs:220`） | property_holds 0.85-0.88 | **property_holds 0.85-0.88** |
| `raw_override_disables` | `load_config`（`config.rs:157`） | property_holds 0.73-0.81 | **property_holds 0.77-0.82** |

**両枝で同じ答え。** 変異はどちらの対象も触らないので、見えるはずがない。
**B の失敗は「ゲートに弾かれた」ではなく「走って、閾値を越えて、壊れたコードを正常と答える」**
——弾かれるより悪い。

**③ `load_config` は無関係な関数ではない。** 固定コミットで `load_config` も
`read_to_string_capped(…)?` を呼ぶ（`config.rs` に 4 箇所ある呼び出しのひとつ）。原文の要求に
無関係ではなく、**変異を入れた経路を外した**のが失敗。広い原文から「関係する関数を 1 つ選べ」と
聞いた結果を、人が事前に選んだ 1 関数との一致だけで採点すると、**対象選択の誤りと確認範囲の
不足が混ざる**。なお B の `fs::read_to_string` は、同じファイルの冒頭コメント
（「`atomic_file::read_to_string_capped` rather than `fs::read_to_string`」）から取った可能性が
高い（確度 60%、未検証）。

**④ C は A と同じ問いに答えていない。** A には「どの呼び出しが失敗し、何を返し、他は成功する」
という条件を渡している。C に渡したのは原文とコードだけで、原文は FIFO・ディレクトリ・symlink の
拒否まで含む広い要求。しかもその拒否を実装する `open_read_regular` の本体は packet に無い。
**C が不足した根拠で `violates` と断定した問題は残るが、A と同じ問いへの成績ではない。**
さらに採点に不整合があった——依存を除いた 6 回も正解を `holds` に置いていたので、C が適切に
`cannot_tell` と答えても不正解になる。実際は 24 回とも `violates` だったので結果は動かないが、
札が誤っていた。

以下の「B が落とした判断」の表は、①を削り、③の言い方を直したもの。

## B が落とした判断

B は**どちらのケースでも答えられる計画を作れなかった**。判定は 1 回も走っていない
（計画が答えられないと判明した時点で止まるので、要求も使っていない）。

| 落とした判断 | 1 件目（`read_baseline`） | 2 件目（`raw_override_disables`） |
|---|---|---|
| **対象** | `read_to_string_capped` ——**呼び先を対象にした** | `load_config` ——**同じ要件に関係する別の呼び出し箇所**。変異を入れた経路を外した |
| **失敗する操作** | 正しい | `fs::read_to_string` ——**そのコードは呼んでいない**（capped 版を通る） |
| **`yields`** | 「エラーを返す（ハングせず、リンク先を読まず…）」 | 同左 |
| **未確認範囲** | `[]` | `[]` |

- **対象の選択が 2 件とも、変異を入れた経路を外した。** 1 件目は要件文に出てくる helper を
  そのまま対象にし、2 件目は同じ helper を呼ぶ別の関数を選んだ。**結果は上の訂正②のとおり、
  両枝で同じ答えになり欠陥が見えない。**
- **`yields` に答えを書いた。** 指示は「操作が返す値であって、答えではない」「何をすべきかを
  書くな」と明示していた。人の計画が `yields` を「`Err(io_error)`」に限っていたのは、偶然では
  なく必要だった。**ただし直し方は「コード中に実在する式に限る」ではない**——`Err(io_error)`
  という文字列がソースに在る必要はない。仮定は**型**で表す（下記）。
- **未確認範囲が空。** 1 関数の確認で要件全体が覆われる、と言っていることになる。
- 「必要な参照先が `[]`」は**B の欠陥ではなかった**（訂正①）。

渡した入力: 要件文 ＋ 対象ファイルの**テスト以外の本体**（21 KB / 44 KB。ファイル全体は
156 KB / 100 KB で、テストが大半）。B に人の計画・変異のラベル・どの枝かは渡していない。

**この分岐に入った。** 不足した判断は上の 4 つ（対象の選択・操作の同定・必要な参照先・
未確認範囲）で、うち**必要な参照先**が 0 件で止まる直接の原因。

**当たらない。** C は品質で負けている（偽陽性 18/18）。費用は C が 24 要求で A が 18 要求＋

## まだ言えないこと

- **2 要件・2 関数・1 モデル・3 回ずつ。** 率ではない。
- **2 件は同じ要件（omamori#468 / PR#476）から来ている。** 3 件目（別リポジトリ）は #19 で
  到達不能により不採用。B は 1 つの要件から 2 つの対象を見つける仕事をしたことになる。
- **B を 1 回しか生成していない**（`temperature: 0`、ケースごと 1 回）。生成のばらつきは
  測っていない。
- **C のプロンプトは 1 つだけ。** 違う聞き方なら違う結果になりうる。C が常に `violates` と
  言うのが、このモデル・この文面の性質なのか、通常レビュー一般の性質なのかは分けていない。
- 費用は要求数とバイト数だけ。Workers AI は neuron 課金で、応答に金額は無い。

## 次

訂正後の壁は**対象と操作の結び付け**ひとつ。参照先は壁ではなかったし、B は走れば自信をもって
誤答する（両枝で `property_holds` 0.73-0.88）ので、**「答えられるか」でなく「欠陥を見分けられるか」**
が測る対象になる。

次は「関数名と条件を自由に書かせる」のをやめ、**実コードから作った候補と、型の決まった失敗条件を
選ばせる**形にする:

1. **確認する性質と採点範囲を分ける。** 「呼び出しが失敗したとき対象が成功として返さない」と
   「その呼び出しが危険な入力を拒否する」は別の主張。証拠不足のときの期待値も、その問いに
   本当に必要な情報から決める（今回の `holds` 固定は誤り）。
2. **対象と操作を、コード由来の ID で選ばせる。** 固定コミットから関数候補と呼び出し箇所を
   列挙し、モデルはそこから選ぶ。選んだ操作が対象の中に実在することを機械的に検査する
   ——存在しない `fs::read_to_string` を条件にする経路はこれで閉じる。
3. **失敗条件を型で表す**（`{"kind":"call_result","callId":"call-12","result":"err"}` のように）。
   **「コード中に実在する式」という制約は操作の指定に使い、`yields` には使わない**——
   仮定する `Err(io_error)` がソースに在る必要はない。質問文は型付きの仮定からコードで組む。
4. **必要な参照先は条件の種類から導く。** 呼び出し結果を仮定した問いと、呼び先の中身を調べる
   問いでは、要る証拠が違う。空の一覧を一律に拒否せず、**未解決の依存が残っているとき**だけ
   保留する。
5. **計画の失敗を段階別に数える**——対象・操作の結び付け／条件の妥当性／必要な証拠／確認範囲／
   最終判定。候補に無い対象や操作は要求の前に止め、意味の誤りは文字列一致でなく
   **事前に作った反例を検出できるか**で測る。

**C の比較は 2 つに分ける。** 同じ条件付きの問いを解かせる比較（Jev の局所判定の価値）と、
原文から始める全体の比較（B が動いてからの構成の価値）。今回の C は後者の入口を、前者の表に
混ぜて置いてしまっていた。

**C についての結論は「今の 1 プロンプト・1 モデルでは構成の優劣を判断できない」まで。**
初版の「Jev を組み合わせる構成を見直す必要は無い」は、比較が同じ問いでなかった以上言えない。
