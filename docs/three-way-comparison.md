# 手書きの計画 / 自動生成した計画 / 通常のレビュー（2026-09-21）

`docs/frozen-spec-v1.md` で凍結した仕組みを、**調整に使っていない実要件 2 件**に当て、
3 方式を同じコード・同じ条件で比べた。

| 方式 | 中身 |
|---|---|
| **A** | 人が書いた計画 ＋ Jev |
| **B** | モデルが書いた計画 ＋ Jev |
| **C** | 通常の LLM レビュー（要件とコードを読んで 1 回で判定） |

B と C は同じモデル（`@cf/meta/llama-3.3-70b-instruct-fp8-fast`＝道具が要件生成に使っているもの）。
計画は `bench/plans/three-way-comparison.json` と `bench/plans/three-way-A-plans.json`、どちらも
送信前にコミット済み。**B は A の計画を見ていない。** ログは `bench/logs/three-way-v1.json`。

## 送信前に分かったこと: 凍結した問いが当たらなかった

`docs/frozen-spec-v1.md` は v4 を凍結した。**新しい 2 件は、1 要求も送る前にそれを壊した。**
v4 のテンプレートは `… returns … at one iteration` と `finite` 欄を持つ——**iterator の形**が
埋め込まれている。新しい対象はどちらも 1 回の呼び出し（`read_to_string_capped(&path, …)?`）で
失敗するので、反復が無い。

**凍結した問いは、最初に出会った新しい失敗伝播の種類に travel しなかった。** 出現の仕方
（`occurrence`）と追加条件（`extra`）をデータに出した **v5**（`bench/check-questions-v5.ts`）を
作った。選択肢・`MEANING`・判定規則・閾値・v4 が足した 3 点はそのまま。**v4 の数字は v5 の
数字ではない**ので、v4 が終了条件を満たしたケースを v5 で測り直した——`staging_info_from` の
出荷版 3/3・変異版 3/3 で、v5 でも成立する。

## 結果（50 要求 / 上限 130、203 KB）

| | 正しい実装 | 変異版（性質を破る） | 挙動不変版 | 偽の違反 |
|---|---|---|---|---|
| **A** | **6/6** | **6/6** | **6/6** | **0/18** |
| **B** | 0/6 | 0/6 | 0/6 | — |
| **C** | 0/12 | 6/6 | 0/6 | **18/18** |

A の確率: 出荷版 `returns_error` 0.94-0.99、変異版 `returns_success` 0.99-1.00、
挙動不変版 `returns_error` 0.95-0.99。**依存を渡さない形は 2 件とも要求ゼロで保留**した。

送信回数: A 18、B 2（計画生成のみ。判定は 0）、C 24、回帰 6。

## C は 24 回すべて `violates` と答えた

`holds` も `cannot_tell` も一度も出ない。**出荷版にも挙動不変版にも「違反」**と答える。

だから **C の「変異版 6/6」は成績ではない**——常に違反と言う方式は、変異版だけを見れば満点に
なる。正しい実装と挙動不変版を同じ表に入れてあるので、それが**偽陽性 18/18** だと分かる。
**正例を測らない比較は、常に「違反」と言う方式を勝たせる。**

C は A と同じコード（対象本体＋`read_to_string_capped`）と同じ要件文を受け取っている。
証拠の不足ではない。

## B が落とした判断

B は**どちらのケースでも答えられる計画を作れなかった**。判定は 1 回も走っていない
（計画が答えられないと判明した時点で止まるので、要求も使っていない）。

| 落とした判断 | 1 件目（`read_baseline`） | 2 件目（`raw_override_disables`） |
|---|---|---|
| **対象** | `read_to_string_capped` ——**呼び先を対象にした** | `load_config` ——**無関係な関数** |
| **失敗する操作** | 正しい | `fs::read_to_string` ——**そのコードは呼んでいない**（capped 版を通る） |
| **必要な参照先** | `[]` | `[]` |
| **`yields`** | 「エラーを返す（ハングせず、リンク先を読まず…）」 | 同左 |
| **未確認範囲** | `[]` | `[]` |

- **対象の選択**が 2 件とも外れた。1 件目は要件文に出てくる helper をそのまま対象にし、
  2 件目はその file の別の関数を選んだ。
- **`yields` に答えを書いた。** 指示は「操作が返す値であって、答えではない」「何をすべきかを
  書くな」と明示していた。人の計画が `yields` を「`Err(io_error)`」に限っていたのは、偶然では
  なく必要だった。
- **必要な参照先を 1 つも挙げなかった。** これが決定打——参照先の検査が保留するので、
  B の計画は 1 回も判定に到達しない。
- **未確認範囲が空。** 1 関数の確認で要件全体が覆われる、と言っていることになる。

渡した入力: 要件文 ＋ 対象ファイルの**テスト以外の本体**（21 KB / 44 KB。ファイル全体は
156 KB / 100 KB で、テストが大半）。B に人の計画・変異のラベル・どの枝かは渡していない。

## 計画が実行前に固定した分岐

> A は通るが B は失敗する → 自動計画のどの判断が不足したかを直す

**この分岐に入った。** 不足した判断は上の 4 つ（対象の選択・操作の同定・必要な参照先・
未確認範囲）で、うち**必要な参照先**が 0 件で止まる直接の原因。

> C が品質・費用ともに有利 → Jev を組み合わせる構成を見直す

**当たらない。** C は品質で負けている（偽陽性 18/18）。費用は C が 24 要求で A が 18 要求＋
保留 2 件なので、C のほうが多い。

## まだ言えないこと

- **2 要件・2 関数・1 モデル・3 回ずつ。** 率ではない。
- **2 件は同じ要件（omamori#468 / PR#476）から来ている。** 3 件目（別リポジトリ）は #19 で
  到達不能により不採用。B は 1 つの要件から 2 つの対象を見つける仕事をしたことになる。
- **B を 1 回しか生成していない**（`temperature: 0`、ケースごと 1 回）。生成のばらつきは
  測っていない。
- **C のプロンプトは 1 つだけ。** 違う聞き方なら違う結果になりうる。C が常に `violates` と
  言うのが、このモデル・この文面の性質なのか、通常レビュー一般の性質なのかは分けていない。
- 費用は要求数とバイト数だけ。Workers AI は neuron 課金で、応答に金額は無い。

## 次

分岐が指す先は「自動計画のどの判断が不足したかを直す」。**必要な参照先**から——B が挙げれば
判定まで到達するので、そこが最初の壁。対象の選択も 2 件とも外れているので、**どちらを先に
直すか**は、参照先を直しても対象が外れていれば意味がないという順序で決まる。

**C についての結論は「Jev を組み合わせる構成を見直す必要は無い」まで。** 1 プロンプト・
1 モデルで、通常レビュー一般の話にはしない。
