# 局所の答えを要件に結ぶ確認計画

Status: Accepted — 2026-09-20。最初の実装範囲は `bench/local-check.ts`。判定処理と公開契約は変更していない。
検討時のコード: `e9e65d8`（PR #10 後）。

## 目的と実験から分かった範囲

Jev には、条件を固定した局所コードの挙動を答えさせる。その回答を、原文の要件に
結びつける規則と、どこまで確認したかの管理は通常のコードで行う。

局所問の実験は開発用 3 件中 2 件、未使用の 2 件中 2 件で正例・反例の双方が
事前の合格条件を満たした。いずれも Rust / omamori であり、全体の正解率や、
要件全体の検証能力を測ったものではない。未使用のケースでも質問文と選択肢は
人が個別に書いているため、質問の自動生成能力は未検証である。

`staging` の失敗原因は未確定とする。実際の問いは「引数がエラーなら次に何をするか」
であり、反例でも `Err(_) => StagingInfo::default()` は存在する。分岐の削除で問いが
無意味になったとは確認できていない。失敗例を残し、質問・参照先の不足・モデルの
判断を切り分ける。

## 採る構造

```text
原文の要件
  → 確認計画（必要な性質、対象範囲、回答との対応）
  → 各場所への結び付け（関数、条件、必要な証拠）
  → Jev の局所回答
  → 規則による性質の判定
  → 要件の判定と未確認部分の報告
```

既存の IntentSpec、探索、証拠作成、JudgmentProvider は再利用する。
最初は bench 内で検証し、`runReview` の既定動作や公開 Status は変えない。
J1 の関連度判定と J5 の探索に関する回答を、要件分解の十分性の証明に流用しない。

## 確認計画に書くもの

| 項目 | 内容 |
|---|---|
| 出所 | 要件 ID、原文の引用、原文と計画の版 |
| 必要な性質 | 要件のどの節を確認するか。条件と観測可能な結果で書く |
| 対象範囲 | 列挙した入口・関数・経路。全リポジトリを覆うとは暗黙に扱わない |
| 局所質問 | テンプレート ID、条件、観測対象、必要な証拠 |
| 回答の対応 | 各選択肢が性質を満たす／反する／未決のどれを示すか、その根拠 |
| 前提 | 呼び出し関係、到達可能性、入力条件など。仮定と確認済み事実を区別する |
| 未確認部分 | 計画が扱わない原文の節、未解決の経路・前提・証拠 |

質問には `cannot_determine` を置く。戻り値や分岐などの観測結果を答えさせ、
正例・反例のラベルや期待回答はモデルへ渡さず採点側に保存する。
最初は固定の質問テンプレートと人が書くパラメーターを使う。実験で使った個別の
質問からパラメーター化する変更も、既存の成功ケースで再検証する。

必要な性質の数と API リクエスト数は同じではない。1 リクエストに複数質問を
まとめてもよい。問いの数は、性質 × 対象経路を判定するために必要な観測から決める。
予算上限で問いを省いた場合は未確認のまま残し、分母から除外しない。

## 局所回答からの飛躍を防ぐ規則

「期待した答えだった」と「要件を満たす」は別々に記録する。

- `returns_immediately` だけでは、エラーを返したのか、部分結果を `Ok` で返したのか
  が分からない。列挙エラーを成功として返さない性質には戻り値の種類も必要。
- `keeps_iterating` だけで違反にしない。残りを読み切って最後に `Err` を返す実装が
  原文の要件に許されるなら、それは有効な別実装である。
- ある `print_warnings` を呼ばないという答えは、stderr に JSON 以外を書かないことの
  一部しか確認しない。他の出力、呼び出し先の副作用、対象となる拒否経路が残る。
- halt 後にフィールドを比較するという答えだけでは、tail truncation を検出して
  結果に反映するところまで確認したことにはならない。

質問の条件を置いただけでは、その条件が実際の対象経路で到達可能とは言えない。
条件付きの局所結果を実際の違反に昇格するには、必要な到達条件と出力への結び付きを
確認する。未解決なら条件付きの観測結果として残す。

最初は、必須の性質をすべて満たす形の要件だけを扱う。任意の論理式や証明言語は
作らない。代替実装を許す性質は、期待する構文ではなく結果に対する規則で表す。
規則で扱えない要件は部分的な検査として報告する。

## 集約

| 状況 | 要件の結果 |
|---|---|
| 要件への対応と必要な前提が成立し、具体的な反例が確認された | VIOLATION |
| 必須の性質が対象範囲の全箇所で満たされ、未確認の節・前提・停止理由がない | VERIFIED。ただし宣言した範囲を明記 |
| それ以外 | UNKNOWN。成功した局所検査と、残った条件を併記 |

空の計画、対象が見つからない計画、未解決の結び付けから VERIFIED を出さない。
回答間に矛盾があれば、その性質は未決にする。確率の平均や多数決で、未知の経路や
欠けた性質を埋めない。0.6 は今回の実験条件であり、製品の誤判定率を保証する値ではない。

この十分性には、二つの異なる確認が必要である。

1. 要件の必要な性質を計画が扱っているか。
2. 宣言した対象範囲の各経路を調べ終えたか。

人やモデルの `complete: true` だけで両方を成立扱いにしない。原文の節との対応、
経路一覧、未確認事項、反例テストを根拠として残す。これは形式証明にはならず、
計画の妥当性は引き続き人の確認と評価に依存する。
現行の読み取り不完全・wrapper の追跡未完了などの停止理由は、局所検査の成功で
自動解除しない。解除するなら、その理由を解消した証拠を別途記録する。

## 誰が問いを立てるか

当面はツールの開発者が、少数の要件について計画と回答対応を作る。Jev は局所の
挙動だけを答え、集約コードが結果を決める。これは評価用の足場であり、すべての PR に
人が質問を書くことを最終的な利用形態にはしない。

将来の自動化は、生成モデルが既存テンプレートと原文の節を対応付けた計画案を作り、
その案を検証する段階として追加する。任意の質問文を生成し、その同じモデルが
「これで要件を覆う」と宣言するだけで VERIFIED へ進める形は採らない。
計画生成の正しさは、局所回答の正しさとは別に、未使用の要件で測る。

## 最初の実装範囲

1. 実験コードと、生の回答・質問・入力を保存する実行器を bench に置く。
2. `collect_listing` の関数内契約を最初の対象にする。
   「入力の列挙でエラーが出たとき、部分一覧を成功として返さない」という条件と結果を
   原文に照合する。これを呼び出し元の表示や元の複合要件全体に昇格させない。
3. エラー時の制御と返す結果の種類を扱う小さな計画・集約処理を実装する。
   先の実験が成功した「即座に止まるか」だけでは完了にしない。
4. 正しい実装、エラーを無視する実装、`return Ok(partial)` に変えた実装を比較する。
   合法な別実装、不要なログの変更、証拠不足も用意し、単なる変更検知を区別する。
5. 同じ問い・集約規則を、未使用のエラー伝播ケースで固定して評価する。

## 最初の実装の結果（2026-09-20、`bench/local-check.ts`、本物の Jev で 6 版 × 3 回）

18 件すべてが事前に書いた期待と一致した。

| 版 | 制御の回答 | 返す結果の回答 | 判定 |
|---|---|---|---|
| 出荷版 | stops_there 1.00 | an_error 1.00 | 覆った性質は満たす |
| エラーを無視 | keeps_going 1.00 | a_success_with_what_it_had 1.00 | VIOLATION |
| 止まるが `Ok(途中まで)` | stops_there 1.00 | a_success_with_what_it_had 1.00 | VIOLATION |
| 最後に失敗する別実装 | keeps_going 1.00 | an_error 1.00 | 覆った性質は満たす |
| ログだけ足した版 | stops_there 1.00 | an_error 1.00 | 覆った性質は満たす |
| 本体が入っていない | cannot_determine 0.74-0.80 | cannot_determine 0.75-0.79 | UNKNOWN |

**「止まるが `Ok(途中まで)` を返す」は制御だけ見ると出荷版と区別がつかない**（どちらも stops_there 1.00）。
返す結果を別の問いにしたので違反として出る。逆に「最後に失敗する別実装」と「ログだけ足した版」は
違反にならない——変更検知ではないことがこの 2 版で確かめられる。

**ここで言えるのはこの範囲まで**: この関数の 6 版について、固定した問いへの回答から
「列挙の失敗を成功として返さない」という性質を判定できた。集約が使っているのは
`on_error_result` 1 つで、**複数の性質を集約する部分はまだ検証していない**。
実行可能な 5 版は、レビュー側で Rust としてコンパイルし、エラーが先頭・途中・末尾にある場合の
挙動を 10 件確認している（この repo のテストでは走らせていない）。

## 2 件目に当てた結果（2026-09-20、`bench/local-check-propagation.ts`）

同じ `QUESTIONS` と `MEANING` を、別の PR・別ファイルの `show_entries`（omamori#558 の head、
`for line in reader.lines() { let line = line?; … }`）に**変えずに**当てた。6 版 × 3 回。

**測ったのは出荷版そのものではない。** 出荷版 `show_entries` の署名は
`(config: &AuditConfig, opts: &ShowOptions, out: &mut impl Write) -> Result<(), AuditError>` で、
読んだ行は `out` へ書き出す。ここで判定させたのは**その読み取りループを、一覧を返す関数に
組み替えた簡略版**（ループ本体は逐語）。1 件目の `collect_listing` と「本体だけが違う」形に
揃えるためで、結果として**この測定は omamori#558 R1 の検証ではない**。

**18 回中 12 回が期待どおり、6 回が外れ。外れたのは全部「出荷版のループと同じ挙動の版」。**

| 版 | 制御 | 返す結果 | 期待と一致 |
|---|---|---|---|
| 出荷版の読み取りループ | stops_there 0.99 | **a_success_with_what_it_had 0.87-0.93** | **×（違反と判定）** |
| 読めない行を飛ばす | keeps_going 0.99 | a_success… 1.00 | ○ |
| 止まるが成功を返す | stops_there 1.00 | a_success… 1.00 | ○ |
| 最後に失敗する | keeps_going 1.00 | an_error 0.69-0.78 | ○ |
| 解析できない行を飛ばす（挙動は出荷版のループと同じ） | stops_there 0.99 | a_success… 0.88-0.91 | **×** |
| 本体なし | cannot_determine 0.97 | cannot_determine 0.85-0.87 | ○ |

**原因は決まっていない。** 読み方が 2 つ残っている:

- **(a) 同じループにあるもう 1 つの失敗について答えている**——`line?`（読み取り失敗、伝播する）と
  `serde_json::from_str` の `Err(_) => continue`（解析失敗、読み飛ばす）の 2 種類があり、問いは
  「項目の 1 つがエラーのとき」としか言っていない
- **(b) `let line = line?;` 自体を「呼び出し元にエラーを返さない」と読んでいる**

「解析できない行を飛ばす」版は 2 種類の失敗を両方残したまま括弧を足しただけなので、(a) と
**整合はするが (b) を否定しない**。分けるには解析失敗を取り除いた版か、伝播を
`match` + `return Err(…)` で書き下した版が要る——それは別の実験で、この数字の読み直しではない。

**閾値では直らない。** 0.95 まで上げれば出荷版のループ（0.87-0.93）は下回って UNKNOWN になり、
本物の違反「止まるが成功を返す」（1.00）は VIOLATION のまま残るので、両者は分かれる。ただし
分かれるのは**判定を降りる**からで、正しいコードに `an_error` を選ばせるわけではない。どの
閾値でも「正しいと判定する」は起きない。

**外れる向きは「正しいコードを違反と言う」側**。レビュアーの時間を使う向きで、欠陥を隠す向き
ではない。ただしこの状態の計画を実コードに向けることはできない。

**分かったこと**: 1 件で成立した問いは、そのままでは travel しない。**問いは「どの失敗について
聞いているか」を名指しする必要がある**（iterator が返すエラーなのか、取り出した値の解析の失敗
なのか）。期待値は書いたまま残し、実行は非ゼロで終わる——持ち越せるかを測っていて、持ち越せな
かったので。

**やらないこと**: 通るまで問いを書き直すこと。それは結果に合わせて問いを作ることになる。
`stops_there` と「成功を返す」の組を矛盾として集約側で潰すのも違う——それは「止まるが成功を
返す」版そのもので、覆った性質に対する本物の違反として残さないといけない。
次の計画は失敗の種類を名指しし、**両方の関数で**、期待値を先に書いてから測る。

## 条件を書いた問い（2026-09-20、`bench/local-check-stated-condition.ts` / `-generalisation.ts`）

2 件目で残した仮説 2 つ——(a) 問いが曖昧、(b) `?` をエラーの返却と読んでいない——を交差させた。
問いの軸は「今の問い」と「条件を書いた問い」、コードの軸は `?` と `match` + `return Err(…)`。
**criteria・`MEANING`・`verdictOf` は据え置き**、変えたのは `instructions` の文面だけ。

条件はケースごとのデータで、テンプレートは `local-check-plan.ts` の `statedQuestions` に 1 つ:

> `code` を読む。**次だけを前提にする**: ファイルのオープンは成功している。`reader.lines()` は
> ある反復で `Err(io_error)` を返す。関数が到達するそのほかの操作はすべて成功する。iterator は
> 有限である。この条件で: 呼び出し元へ何を返すか。

答え（「伝播する」）は条件に入れない。`yields` は**操作が返す値**であって挙動ではない。

2 版が同一挙動であることは Jev に聞く前に確かめた（`bench/rust/propagation-equivalence.rs`、
`rustc --test`。11 入力で両者一致、差のある版がエラーを含む 8 入力すべてで落ちることも検査）。

### 結果: 効いたのは文面のほうで、コードの書き方ではなかった

| コード | 今の問い | 条件を書いた問い |
|---|---|---|
| `?`（出荷版のループ） | a_success 0.87-0.88 — 誤り | **an_error 1.00 — 正しい** |
| `match` + `return Err(…)` | a_success 0.49-0.59、閾値割れで UNKNOWN — 誤り | **an_error 1.00 — 正しい** |
| 読めない行を飛ばす（違反） | a_success 1.00、違反 — 正しい | a_success 0.93-0.94、違反 — 正しい |
| 止まるが成功を返す（違反） | a_success 1.00、違反 — 正しい | a_success 0.95-0.97、違反 — 正しい |

予測は (b) で、外れた。書き下しても直らないどころか確信が下がって閾値を割った。予測の根拠に
した `fails-at-the-end` の `an_error` 0.69-0.78 は、末尾で `match failure { … }` を返す別の形で、
「明示的だから」という帰属は何にも支えられていなかった。

**ここで決まったことと、決まっていないこと。** (b) は否定された——条件を名指しすれば `?` は
1.00 で「呼び出し元へエラーを返す」と読まれる。**(a) は確認できていない。** 24 回が支持するのは
「この条件を書いたら、両方の書き方で戻り値を正しく答えられた」までで、**以前の誤答が解析失敗を
指していたかどうかは分かっていない**。足した文面の別の性質が同じ働きをした可能性を、この実験は
切り分けていない。原因の断定はここで追わず、狭い結論のまま進む。

### 当てていない 2 つで確かめた（ただし範囲は狭い）

- **`collect_listing`**（iterator が引数・失敗が 1 種類、条件データも別）: 今の問いも 12/12、
  条件を書いた問いも 12/12
- **`map_err(|e| …)?`**（`verify_chain` から逐語。3 つ目の書き方）: 今の問いは
  a_success 0.79-0.88 で **0/3**、条件を書いた問いは an_error 0.99-1.00 で **3/3**
- **`map_err` で作ったエラーを `else { continue }` で捨てる版**: どちらも 3/3 で捕まえた

**「未使用の実要件 2 件で成立した」ではない。** `collect_listing` は 1 件目で使った関数そのもので、
新しいのは**条件データが別**という点だけ。`map_err` も関数まるごとではなく、同じ簡略 wrapper の
中の 1 行が実物。どちらも測る値はあるが、種類が違う。さらに**条件データも問いの一部**で、
`collect_listing` の条件は答えを見たあとに書き直している（下記）ので、その 12/12 は
**書き直した条件の確認**であって、手つかずの初回測定ではない。固定されていたのはテンプレートで、
データではない。

2×2 と合わせて 60 回、各版のコードの実挙動と照合（保存ログから数え直し）:

| 指標 | 今の問い | 条件を書いた問い |
|---|---|---|
| 判定がコードと一致 | 21/30 | **30/30** |
| 結果の選択肢が一致 | 21/30 | **30/30** |
| 結果の選択肢が一致、かつ 0.6 以上 | 21/30 | **30/30** |
| 制御の選択肢が一致 | 30/30 | 27/30 |
| 制御の選択肢が一致、かつ 0.6 以上 | 30/30 | 25/30 |
| 正しいコードを正しいと言えた | 6/15 | **15/15** |
| 本物の違反を捕まえた | 15/15 | 15/15 |

**制御の下 2 行は別の数字なので分けて書く。** `map-err/discards` の 2 回は正しい `keeps_going` を
選んでいるが確率 0.51 で閾値を割っている。今の `verdictOf` は結果の問いしか見ないのでどちらも
判定を動かさないが、制御に重みを持たせた瞬間に効く。

**今の問いが外した 9 回はすべて「同じループに失敗が 2 種類ある」ケース**で、3 つの書き方が
全部そこで外れる。失敗が 1 種類の `collect_listing` では今の問いも完璧。曖昧さは文面単独では
なく**文面とループの形の組**にあった。

**代償**: 条件を書いた問いの外れ 3 回はすべて「続行する版の制御の問い」で、結果と判定は正しい
まま。判定には出ないので、ここに書く。

**途中で 1 回、条件の書き方を直した。** `collect_listing` の条件に「`seen` は空」と書いたところ、
「止まるが成功を返す」版が 3 回とも `a_success_with_nothing`（0.67-0.75）を返した。

**この答えは誤りではない**——最初「前提が偽だった」と書いたが、それが誤りだった。条件は
**エラーが何番目に出るか**を言っていない。`Err(_) => return Ok(seen)` はエラーが 1 番目なら
`Ok([])`、2 番目なら `Ok(["before"])` を返す（`rustc` で確認）。どちらもこの条件で起こりうる。
しかも選択肢が重なっている——「集めたものを成功として返す」は「何も集まっていない場合」を含む。
欠陥は**条件が時点を言っていないことと、選択肢が排他でないこと**で、前提の真偽ではない。

ある。全 5 本の一覧は `bench/logs/README.md`）。ただしこの再実行は**書き直した条件の確認**であって、独立した

書かない。エラーの位置を固定するのは**やっていない**——問いの内容が変わるので、別の実験。

ケースの採用条件、期待する挙動、成功・失敗・未決の扱いは実行前に保存する。
変異版はローカルのテストなどで意図した挙動差があることを確認する。
ログには commit、対象位置、原文と計画と質問の hash、送信 packet、丸めない全回答、
閾値、局所結果、集約理由、要求数・送信量を残す。秘密情報の既存の除外・伏字を維持する。

この一件が端から端まで成立してから、呼び出し元への伝播、stderr 出力などへ広げる。
既存の 32 要件すべてへの自動計画生成、汎用の証明グラフ、通常レビューの判定変更は
この最初の実装には含めない。
