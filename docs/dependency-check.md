# 対象の欠陥と依存の欠陥を分けられるか（2026-09-20）

`docs/evidence-selection.md` の続き。前回は「関連証拠をどう選ぶか」を 4 条件で比べて候補の規則を
落とした。**その結論は交絡していた**（下記）。ここでは交絡を外し、**問いの形**を変えて測り直す。

計画は `bench/plans/omamori-553-r2-dependency.json`（送信前に確定）。実行器は
`bench/dependency-check.ts`、ログは `bench/logs/dependency-check-v1.json`。

## 結論を先に

**終了条件を満たした。** 必要な依存を packet に入れた状態で、**対象だけを変えた欠陥**と
**依存だけを変えた欠陥**の両方を、v4 の問いは 3/3 で区別する。

そして**私の予測は 2 つとも外れた**。難しいのは依存側だと思っていたが、依存側は v3 でも
できていた。v4 で変わったのは**対象を変異させた版の確信**で、0.50-0.67（採用 1/3）から
0.84-0.86（3/3）になった。

## 前回の結論を訂正する

`docs/evidence-selection.md` は「効くのは種類でも量でもなく、関連証拠が 1 件でもあるかどうか」
「『必要』と宣言した呼び先自身が答えを悪くする」と書いた。**交絡していた。**

| 条件 | `collect_listing` | それ以外 |
|---|---|---|
| 現状 | あり | 呼び元・テスト×2 |
| テスト除外 | あり | 呼び元 |
| 呼び先だけ | あり | なし |
| 関連なし | **なし** | なし |

**「空でない」と「`collect_listing` を含む」が完全に一致している。** 無関係な関数 1 件だけ、
呼び元だけ、という条件は測っていない。あの 4 条件から確定できたのは
**「テスト除外だけでは合格条件を満たさない」「呼び先だけ残した形では安定して区別できない」**
の 2 つだけ。量の影響もテストの期待値の影響も、断定できる状態ではなかった。

さらに今回の結果が**積極的に否定**する: **同じ `collect_listing` を入れたまま、問いの文面を
変えるだけで 0.49 → 0.85 になる**。関連証拠が毒なのではなく、**問いが「誰の戻り値か」を
言っていなかった**。

## 「呼び先なしで正答した」も、呼び先が不要な証拠ではなかった

これはモデルを使わずに決着する。**`dep-mutant`**——`collect_listing` だけを 1 行変えて
per-entry のエラーを握り潰させ、**`src/cli/doctor.rs` は 1 バイトも変えない**版を作った
（`git diff correct dep-mutant -- src/cli/doctor.rs` は空）。

- `correct`: 呼び先が伝播する → `staging_info_from` は **`Err` を返す**
- `dep-mutant`: 呼び先が握り潰す → 同じ `staging_info_from` が **`Ok` を返す**

`cargo test --lib staging_listing_that_stops_partway_is_reported_as_unreadable` で実測:
`correct` は通り、`mutant` と **`dep-mutant` は同じ `got "  [Staging] empty\n"` で落ちる**。

対象本体は同じ bytes（ハッシュ `6c8404049130` が一致、実行器が毎回検査する）。したがって
**呼び先を外した packet は、この 2 つを区別できない——同じ入力に正解が 2 つある**。そこで
出た答えは、当たっていても推測でしかない。

前回「呼び先が要るという前提は測定と合わない」と書いたのは誤り。**「答えられた」を
「根拠があった」と読み替えていた。** 参照先の検査が推測を保留するのは欠陥ではなく仕事。

## v4 の問い

criteria・`MEANING`・判定規則・閾値は v3 のまま（**同じオブジェクトを再利用**、テストで固定）。
変えたのは `instructions` だけ——それでも契約の変更なので、v3 の数字は v4 の数字ではない。
同じセッションで両方を測る。

> `code` は `staging_info_from` の本体。`evidence.related` にあるのはこの関数が呼びうる
> 別のコードで、その呼び出しが何をするかを割り出すために渡してある。**問いの対象ではない。**
> （条件）… この条件で: **`staging_info_from`** は呼び出し元へ何を返すか。
> **`evidence.related` のどれかの関数が何を返すかではなく、`staging_info_from` がそれをどうするか。**

packet は `callee-only`（対象本体＋`collect_listing` 1 件）。問いが答えられる最小の形で、
テストの期待値も入らない。**`buildEvidence` の既定の形は今回測っていない。**

## 結果（21 要求 / 上限 30、94 KB）

| セル | コードの実挙動 | 答え | p(真) | 0.6 越え |
|---|---|---|---|---|
| **v4** 両方出荷版 | returns_error | returns_error | 0.98 | **3/3** |
| **v4** 対象を変異 | returns_success | returns_success | 0.84-0.86 | **3/3** |
| **v4** 依存を変異 | returns_success | returns_success | 0.86-0.91 | **3/3** |
| v3 両方出荷版 | returns_error | returns_error | 0.98-0.99 | 3/3 |
| v3 対象を変異 | returns_success | returns_success | 0.50-0.67 | **1/3** |
| v3 依存を変異 | returns_success | returns_success | 0.81-0.85 | **3/3** |

**v3 でも依存を変異した版は 3/3 で読めていた**（0.81-0.85）。つまりモデルは最初から依存を
**使って**いた。

**確定したのはここまで**: **対象と依存の役割を明示すると、正しい答えが安定して採用基準を通る。**
対象を変異させた版で v3 は 0.57 / 0.67 / 0.50、v4 は 0.84 / 0.86 / 0.85。

> **注意（訂正）。** この節の初版は「できていなかったのは帰属で、`collect_listing` の `Err` を
> 対象の戻り値として答えていた」と書いた。**同時測定の v3 は 3 回とも `returns_success`（正しい
> 側）を選んでいる**——低いのは確率だけで、選択そのものは間違っていない。取り違えの説明は、
> `#17` の同じケースで選択が `returns_success` / `returns_error` / `returns_success` と割れた
> ことと整合する**仮説**であって、確定していない。これを確定させる追加実験は、次へ進む条件に
> しない。

## 参照先を渡さない形は、やはり推測する（診断）

`no-dependency`（対象本体だけ、関連証拠なし）を、参照先の検査が保留した上で**診断として
送った**。v4 でも `cannot_determine` とは言わず、**`returns_error` を 0.92-0.93 で返す**。

表には 3/3 と出るが、**これは合格ではない。** この packet（`51862343ccd1`）は `correct` 由来でも
`dep-mutant` 由来でも同じ bytes で、後者なら正解は `returns_success` なので**同じ答えが 0/3 に
なる**。当たっただけ。

**参照先の検査は、モデルがやらない仕事をしている**——これが今回いちばん実用的な確認。

## まだ言えないこと

- **1 要件・1 関数・2 種類の変異。** 率ではない。
- **`buildEvidence` の既定の packet（`as-is`）では測っていない。** テストの期待値が入る形で
  v4 がどうなるかは未測定。前回 v3 の `as-is` は 0.44 だった。
- **なぜ v3 の確率が低いのかは分かっていない。** v4 で上がったという事実だけ。取り違え説は
  仮説（上の注意）。
- `no-dependency` を v3 で送っていない（v4 の診断のみ）。

## 次

計画が実行前に固定した分岐に従う:

> 3 つとも 3/3 を越えたら、規則を固定して未使用ケースと、計画の自動生成との比較へ進む。

**進める。** ただし固定するのは「v4 の問いの形 ＋ 参照先の検査」であって、証拠の選び方
（`no-tests` 等）は**まだ採用していない**——`as-is` で v4 を測っていないので。

`builder.ts` の呼び出し箇所収集がテスト領域を除外していない件・同じ範囲を 2 回送る件は、
**コードと通常のテストだけで正当化できる独立した修正**として切り離す。Jev の誤答が直ると
主張しない（今回、テストが入ったままの形は測っていない）。
