# 実験用 CLI（2026-09-21）

`docs/selection-materials.md` の続き。もう一枚の選択成績表ではなく、**コードを渡すと根拠付きの
結果が返るコマンド**を作った。

```sh
jev-intent-review --experimental-local-check --base <rev> --head <rev> --intent-spec <file>
```

**利用者は対象ファイル・関数・call ID・期待回答を入力しない。** 製品コードに評価用の名前も
入っていない。

## 経路

1. **要件の語でファイルを開く**（既存の字句探索）
2. **計画側のモデルが、固定コミットから作った一覧の call ID を選ぶ**（`src/plan/planner.ts`）。
   各選択に「原文のどの節か」を書かせる
3. **選ばれた関数の中を機械的に広げる**——選択は「要件がそこにある」と言っているが、欠陥は
   同じ本体の別の呼び出しであることが多い（実測: 正しい関数に 3/3、正しい呼び出しに 1/3）
4. **問いを置ける候補だけ判定する**（`src/plan/applicability.ts`）。呼び先の**定義を引いて**
   `Result` を返すと確認できたものだけ。確認できないものは理由付きで残す
5. **予算は関数ごとに 1 件ずつ**割り当てる（`roundRobin`）。呼び出しの多い 1 関数が run を
   占めないように

**局所の観測は要件の判定ではない。** 計画が「どの節か」を言った呼び出しの観測だけが要件に
かかる。呼び先が `Result` を返すと分かるのは**問いが置ける**ということであって、
**そこでその性質が要求される**ということではない——失敗を診断に記録して続ける関数は実在する。
**この経路は違反を報告しない。**

## 先に直した 3 件（どれもテストで固定）

**① 適用検査が行を見ていた。** `if p.exists() || p.symlink_metadata().is_ok()` の `exists()` が
通っていた——隣の呼び出しの `.is_ok()` を見ていた。`Option::unwrap_or` も通った。
**定義を引いて署名で決める**形に変えた。標準ライブラリのメソッドは定義が無いので保留になる。

**② 正解の識別が呼び先の名前だった。** 同じ本体の `read(a)` と `read(b)` を区別できなかった。
**呼び出し式**に変えた。今の 2 ケースの数字は動かないが、**関数の中を広げると同名の呼び出しが
複数入る**ので必要。

**③ 署名を 1 行しか読んでいなかった。** Rust は署名を折り返すので、
`fn create_staging_subdir(` だけ読むと戻り値が見えず、**折り返し署名の関数がすべて
「Result を返さない」として保留**されていた。実機で気づいた——レポートに
「create_staging_subdir does not return a Result」と出て、実際は `Result<PathBuf, String>` だった。
**黙った拒否は、考えた末の判断のように見える**ので質が悪い。

## 実機の結果

固定コミットの omamori に対して、要件を固定して（`--intent-spec`）実行:

| 枝 | 開いたファイル | 観測 | 未確認 | `read_baseline` に到達 |
|---|---|---|---|---|
| correct | `src/audit/mod.rs`, `src/actions.rs` | 4 | 86 | **いいえ** |
| m-read-baseline | 同じ | 4 | 86 | **いいえ** |

**経路は通り、要件を固定すれば決定的**（2 回とも同じファイル・同じ件数）。
**ただし終了条件は満たさない**——変異した呼び出しに届いていない。

**理由は特定できている: ファイル選択も要件の語で行っている。** 原文は症状（FIFO・
ディレクトリ・symlink）を名指し、機構（共有の読み取りヘルパ）を名指さない。
`#24` で呼び出しの選択に起きたのと**同じ失敗が、ファイルの段でも起きる**。

`--intent`（自由文）だと要件を書くモデルが毎回別の文に直すので、**開くファイルが run ごとに
変わる**。比較するときは `--intent-spec` で固定する。

## 終了条件に対して

| 条件 | 状態 |
|---|---|
| CLI から両ケースの変異した呼び出しへ届く | **未達**（ファイル選択が別の場所を指す） |
| 正例・変異版・挙動不変版を区別できる | 未達（届いていないので比較にならない） |
| 正例・挙動不変版に誤った違反を出さない | **満たす**——この経路は違反を報告しない |
| 未対応・適用未確定・予算外が理由付きで残る | **満たす**（86 件が理由付きで「Not checked」に） |
| 個別の関数名・正解ラベルが製品側に無い | **満たす**（`src/plan/` と `src/review/local-check-run.ts` に固有名詞は無い） |

## 次

壁はもう**ファイルの選び方**ひとつに寄っている。要件の語からでは、機構のあるファイルに届かない。
`#25` の測定が指していたのと同じ場所——**語は順位付けに使い、到達の手段は別に要る**。

変更された行から始める（この道具の元の考え方は「diff は探す手がかり」）か、
一次資料の段落から機構の名前を取りに行くか。どちらも `--experimental-local-check` の
ファイル選択を差し替えるだけで測れる。
