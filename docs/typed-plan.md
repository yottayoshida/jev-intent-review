# 実在する id で選ばせる（2026-09-21）

`docs/three-way-comparison.md` の続き。#21 で残った壁は 1 つ——**原文を実在の関数・実在の
呼び出しに結び付けること**。自由記述をやめ、**固定コミットから作った候補を id で選ばせる**形に
した。

実装は `bench/code-candidates.ts`（列挙）・`bench/typed-plan.ts`（型と検査と条件生成）・
`bench/typed-plan-check.ts`（実行器）。ログは `bench/logs/typed-plan-v1.json`（器具に欠陥）と
`bench/logs/typed-plan-v2.json`（直したあと）。

## 形

**A も B も同じ機構を通り、違うのは「誰が id を選ぶか」だけ。**

計画はこの形しか取れない:

```json
{ "property": "call_failure_not_returned_as_success",
  "targetId": "function-7",
  "failure": { "kind": "call_result", "callId": "call-20", "result": "err" },
  "notCovered": ["…"] }
```

- **実在の制約は「操作」に掛け、仮定には掛けない。** `targetId` と `callId` は固定コミットから
  作った一覧の中にしか無く、要求を送る前に検査する。一方 `Err(io_error)` のような**仮定は
  ソースに在る必要がない**——`result: "err"` という**種類**であって文字列ではない。
- **条件は生成する。** `conditionFrom` が組むので、**答えを書き込む欄が存在しない**。#20 で
  `yields` に「エラーを返す（ハングせず…）」と書かれた経路は、欄ごと消えた。
- **必要な参照先は種類から導く。** `call_result` は呼び先の結果を仮定しているので参照先は不要
  （`bench/logs/referent-needed-v1.json` で実測、12/12）。一律に 1 件以上を要求しない。
- **却下は段階別。** `shape` / `property` / `target` / `call` / `binding`。「存在しない関数を
  名指した」と「他の関数の中の呼び出しを名指した」は別の失敗として数える。

列挙は製品の `definedName` / `blockEnd` / `testRegions` を使う（テスト領域は候補から外れる）。
ただし `definedName` は `let path = …` も拾うので、**`fn` の後に同じ名前が出ることを要求して
いる——この列挙は Rust 専用**。別言語は別の行が要る。

## 途中で見つけた自分の欠陥（v1 → v2）

初版の条件は `Execution reaches line 322, \`let content = crate::atomic_file::read_to_string_capped(path, …)?;\`` と
**行を引用**していた。**変異はまさにその行を書き換える**（`let Ok(content) = … else {`）ので、
**条件が、見せている本体と矛盾する**。

実測（`typed-plan-v1.json`）: `raw_override_disables` の変異版が **1/3**（0.65 / 0.49 / 0.50）。
引用をやめて「`read_to_string_capped` の呼び出しに到達する」と名指すだけにしたら **3/3**
（`typed-plan-v2.json`）。

**条件は、比べる版をまたいで成り立たないといけない。行番号とソース行は、変異が動かす 2 つ。**
テストで固定した（`test/typed-plan.test.ts`「the condition holds across the versions being compared」）。

## 追記（v3）: id が質問まで保たれていなかった

v2 の条件は**呼び先の名前だけ**を使っていた。同じ関数の中に同じ呼び先が 2 回あると、
**異なる `callId` から同一の条件**が出る:

```rust
let first  = read_to_string_capped(a, 100)?;                    // 伝播する
let second = read_to_string_capped(b, 100).unwrap_or_default(); // 握り潰す
```

前者と後者で答えは逆なのに、質問文は同じ。ローカルで再現した（今はテスト）。

**直し方**: 条件が運ぶのは**呼び出し式**（`read_to_string_capped(&path, MAX_TRACKED_FILE_BYTES)`）。
行の引用（v1）でも呼び先の名前（v2）でもない、**扱い方が変わっても残り、同じ関数の別の呼び出しとは
区別できる**情報。あわせて、判定前に **`locateCall` がその版の本体で一意に結び直せるかを検査**する
——0 件なら版が動かした場所、2 件以上なら条件がどちらか言っていない。どちらも要求を送らずに保留。

実測（v3、38 要求）: **成績は v2 と同じ**（A 18/18、B は両ケースとも版を分けられない）。
**保留は 0 件**——呼び出し式は 5 つの版すべてで一意に結び直せた。指摘のとおり
「18/18 を否定する問題ではない」が、候補を広げると必要になる。

なお実際に効いている: B が選んだ `load_config` 側は `read_to_string_capped(&path, …)`、
A の `raw_override_disables` 側は `read_to_string_capped(path, …)` で、**`&` の有無で区別**される。

## 結果（v2・v3 で同じ、38 要求 / 上限 50、202-205 KB）

| | 正しい実装 | 変異版 | 挙動不変版 | 版が分かれるか |
|---|---|---|---|---|
| **A**（人が id を選ぶ） | 3/3 ・ 3/3 | **3/3 ・ 3/3** | 3/3 ・ 3/3 | **2 件とも分かれる** |
| **B**（モデルが id を選ぶ） | 0/3 ・ 3/3 | 3/3 ・ 0/3 | 0/3 ・ 3/3 | **2 件とも同じ答え** |

（各セルの 2 つの数字は `read_baseline` ・ `raw_override_disables`）

**A は 18/18。** しかも**人が書いたのは 2 つの id だけ**——条件も問いも参照先も生成で、
散文の条件は 1 行も書いていない。#20 の A（手書きの条件＋不要な参照先）と同じ成績を、
**入力を 2 つの id に縮めて**出した。

**B は 2 件とも版を分けられない。** 選んだのは `generate_baseline`（呼び出しは
`fs::read_link(&link_path)`）と `load_config`。どちらも**計画としては整合**している——
binding 検査を通り、操作は実在し、参照先も要らない。**変異が届かない場所を見ているだけ。**

## 何が直り、何が残ったか

| #20 で挙げた失敗 | 今 |
|---|---|
| 必要な参照先 `[]` | **失敗ではなかった**（#21 で訂正） |
| `yields` に答えを書く | **欄が消えた**——書き込めない |
| 実在しない操作（`fs::read_to_string`） | **止まる**——id は一覧の中にしか無い |
| 未確認範囲 `[]` | B は `["directory","FIFO"]` を書いた（空ではなくなった。中身の妥当性は未評価） |
| **対象の選択** | **残った。これだけ。** |

**計画を検査できるようにしても、正しくはならない。** id 制が止めたのは「言った通りの場所が
無い」であって、「間違った場所を選ぶ」ではない。

## まだ言えないこと

- 2 要件・2 関数・1 モデル・3 回ずつ。**率ではない。**
- B は各ケース 1 回生成（temperature 0）。ばらつきは測っていない。
- 一覧は**一部が欠けている**——`integrity.rs` で呼び出し 84 件、`config.rs` で 61 件が上限で
  落ちた（`omitted` に記録）。**対象 2 件の呼び出しは全部入っている**ことは確認したが、
  別の対象なら落ちていた可能性がある。
- `notCovered` の中身は採点していない。
- 列挙は Rust 専用。

## 次: 1 組を当てるのではなく、集合を選ぶ

B が選んだ `load_config` は**原文に関係する場所**で、そこでエラーを伝播すると答えること自体は
正しい。問題は、その 1 か所を確認しても**同じ要件に属する `raw_override_disables` の欠陥が
見つからない**こと。これは選択の誤りだけでなく、**確認範囲の不足**。

固定コミットから数え直すと、同じ呼び先を使う箇所がこれだけある:

| ファイル | 呼び出し（列挙） | うち `read_to_string_capped` |
|---|---:|---:|
| `integrity.rs` | 284 | 6 |
| `config.rs` | 276 | 4 |

`config.rs` の 4 か所は `load_config` / `raw_rule_names` / `read_raw_rule_state` /
`raw_override_disables`。**関連する読み取りを 1 つ見つけたら、同じ呼び先の箇所へ機械的に
広げられる。**

**ただし同じ呼び先の 10 か所すべてに「失敗したら `Err` を返すべき」を当ててはいけない。**
診断結果に失敗を記録して続ける関数など、別の扱いが正しい場合がある。**共通の呼び先は探索の
手掛かりであって、その性質が要求される根拠は原文との対応で別に確認する。**

次の測定で分けて数えるもの:

- 既知の変異箇所が候補集合に**入ったか**
- その欠陥を**検出できたか**
- **無関係な箇所から違反を出していないか**（正例・挙動不変版で偽の違反を増やさない）
- 要求数
- **未確認のまま残った箇所**（一覧の上限や予算で落ちた分を含む）

比べるのは「今の 1 組選択」「複数選択」「複数選択＋同じ呼び先への展開」。質問・閾値・判定規則は
共通にする。**成功条件は選択数を増やすことではない。**

**一覧には今回も上限で落ちた呼び出しがある**（`integrity.rs` 84・`config.rs` 61）。だから
選んだ候補が全部通っても、それだけで要件全体を VERIFIED にはできない。
