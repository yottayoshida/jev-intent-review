## 1. 問いと採点の契約を固定する

今回の性質は「特定の列挙操作が失敗したとき、それを関数の成功として返さない」に限定する。
対象は既存実験と同じ Rust の `Result` と iterator の範囲にする。新しい言語・出力先・非同期処理を
同時に検証対象へ増やさない。

返す結果の選択肢を、`returns_error` / `returns_success` / `cannot_determine` の排他的な3つにする。
成功値の空・非空は問わない。有限性などの前提があっても結果が一意に決まらない場合は未決にする。
既存実験を上書きせず、新しい質問の版として追加する。これは質問契約の変更なので、過去の30/30を
そのまま新しい質問の成績には使わない。

質問は毎回同じテンプレートから作り、両方の問いが単独で同じ条件を参照できるようにする。
制御の問いは当面診断用のままにし、判定への重みや多数決を追加しない。
各回答について「選択肢が合ったか」「選択肢が合い、採用閾値も通ったか」を別々に記録する。
閾値は実験値の0.6で固定し、確率差や測定後の閾値変更で正解を作らない。

## 2. 対象と確認計画を、モデルへ送る前に保存する

局所問の調整に使っていない実要件と関数を1組選ぶ。既存の `collect_listing`、`show_entries` の
簡略版、既知の wrapper に構文だけを移したものは新しい対象に数えない。
要件と対象を選んだ理由、既存実験への使用歴を記録し、回答を見てから対象を差し替えない。

選ぶ要件は、原文にエラーを成功として扱わない要求があり、対象となる列挙操作と、その結果を返す
関数の対応を説明できるものにする。短い実関数と必要な型・補助関数が既存の証拠サイズに収まる
ものを優先する。適した対象が見つからなければ、採用できなかった理由を報告し、要求を創作しない。

`bench/corpus/` の要件は自動生成後の機械修復で、正解ラベルも付いていない。
それだけを原文や正解として扱わず、GitHub の issue / PR などの一次資料を読んで照合する。

確認計画には少なくとも以下を含める:

- 原文URL、取得時点、保存した原文の該当節、要件ID、確認する性質とその対応理由。
- 対象リポジトリ、固定コミット、ファイル、関数、対象操作、その識別根拠。
- 操作が返す入力値、前提が成立する時点、他の操作や有限性の仮定。仮定と確認済み事実を区別する。
- 各回答を性質の充足・違反・未決へ対応させる規則。期待回答や「伝播するべき」は送信条件に入れない。
- 対象範囲、必要な証拠、元の要件のうち確認しない節・経路・前提。
- 正例・変異版ごとの期待結果、実行回数、採点方法、要求数の上限。

条件データも質問の一部として版とhashを固定する。「ある時点で空」という仮定から、
別の時点でも空だと推論しない。複数の挙動が条件を満たすなら、判定対象の性質が一意に決まるかを
確認し、決まらなければ未決にする。

## 3. 実コードから証拠を作る小さな実行器を作る

`Git`、`Discoverer`、`buildEvidence`、既存の秘匿処理と `JevProvider` を再利用する。
人が指定したファイル・関数・操作を固定コミットに結び付ける部分は bench 側でよい。
今回は自動で対象を発見する能力や、モデルが確認計画を生成する能力は測らない。

実関数の署名、戻り値、関数本体をモデル用に書き換えない。既存の切り出しが失敗した場合は記録する。
コピーしたコード文字列や、成功値を返すように作り直した wrapper で代用しない。
必要な型や呼び先は、出所を持つ関連証拠として渡す。テスト用の入力注入とモデルへ送る実コードは
区別し、どこを補助したか残す。

対象が一意に決まらない、必要な本体が切れている、判定に必要な前提・参照先が欠けている場合は
UNKNOWN と理由を出す。高いモデル確率でこの不足を解除しない。
既存の停止理由や切り出し制限を緩める変更が必要になったら、それをこの実験の成果に混ぜない。

## 4. 先に期待値を書き、局所の挙動を実行で確認する

同じ対象から、最低限次の4条件を作る。モデルの回答を正解ラベルの根拠にはしない。

| 条件 | 性質について期待する結果 |
|---|---|
| 原文に対応する正しい実装 | 満たす |
| 指定した操作の失敗を成功として扱う変異版 | 違反 |
| その性質を変えない変更版 | 正しい実装と同じ |
| 判定に必要な本体・参照先が欠けた証拠 | UNKNOWN |

変異版は実リポジトリの隔離したコピー上の最小差分とし、対象の本体を維持したまま作る。
ローカルテストで、注入した失敗が対象の操作で実際に発生し、正例・変異版の観測結果が期待どおり
異なることを確認する。継続や読み取り回数を主張するなら、戻り値だけでなくその事実も観測する。

合格条件は実行前に固定する: モデルを使う各条件を3回測り、正しい版・違反版・挙動不変版は
各条件ごとに期待した選択肢が0.6以上で3/3採用されること。1回でも外れればその条件は未達として残す。
証拠不足はローカルの不足判定でUNKNOWNにできることを必須にし、不要なAPI要求を送らない。
この小標本で一般の精度や誤判定率を主張しない。

新しい質問版を既知ケースで回帰確認してから、固定した実要件へ適用する。
回帰確認と新しい対象の結果は別集計にする。最初の測定は合計30 HTTP要求以内（再試行を含む）を
目安に計画し、実行前に内訳とハード上限を保存する。超過するなら対象や反復数を無断で削らず、
必要性を説明して計画を確定し直す。
認証情報は既存の正規経路を使う。実測に必要な権限・認証がない場合も、実装・ローカル検証と
レビュー可能な送信内容の準備までは完了する。

## 5. 結果を三つの段階で報告する

1. 局所の観測: 何を返すと答えたか、確率、採用可否。
2. 性質の判定: どの原文の節について、どの条件・範囲で満たす／違反／未決か。
3. 元の要件の状態: 確認できた節と未確認の節・経路・前提。

局所の成功を元の要件全体の VERIFIED に昇格させない。違反も、対応する原文の節と、反例が実際に
成立する条件を示してから主張する。空の計画や、対象を見つけられなかった計画は成功にしない。

実験結果に応じた次の判断は以下で固定する:

- 正例・反例・不変変更・証拠不足が期待どおりなら、次の段階として通常レビューに実験モードで
  接続する計画を提案する。既定の判定・exit codeはその時点でも自動変更しない。
- 人が条件を書いても実関数では外れるなら、失敗した packet とケースを保存し、統合へ進まない。
- 原文と性質が結び付かない、または証拠が足りないなら、その不足を今回の結果として報告する。

回答を見て質問・条件・期待値を変える必要が出た場合は、元の結果を保存し、新しい版として扱う。
そのケースは以後の開発用とし、修正後の成功を未使用ケースへの成功とは数えない。
